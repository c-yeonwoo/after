# 오피스타운 1:1 프라이빗 매칭 — MVP 구현 계획

## 확정된 답변 반영

- 첫 허브: **테헤란로·역삼권** 단일 허브
- 직장 인증: **회사 이메일 인증** (도메인 + 인증코드)
- 사적 채팅 오픈: **만남 전날 00:00**
- 클라이언트: 반응형 웹 (모바일 우선), 백엔드는 Lovable Cloud

### 서비스명 제안 (임시)

**「퇴근길」** — 영문 표기 `toegeun.kil` / 슬로건: *같은 퇴근길에서, 호감 있는 한 사람과, 카페 한 잔.*
대안: 「여섯시」(정시 퇴근·하루의 전환), 「한 잔 거리」.
→ 우선 「퇴근길」로 구현하고 언제든 한 곳(브랜드 상수 파일)에서 교체 가능하게 둡니다.

## 톤 & 비주얼 방향

계급·클럽 카피 금지(D8). 저녁 퇴근 시간대의 차분한 톤: 딥 네이비 배경 + 따뜻한 앰버 액센트(카페 조명), 여백 넉넉한 단일 컬럼, 카드 최소화. 스와이프 제스처·피드형 UI는 만들지 않음.

## 단계별 구현 (각 단계가 하나의 승인 게이트)

### Step 1 — 랜딩 + 온보딩 골격 (백엔드 없이)
- `/` 랜딩: 문제·루프 3단 설명, 카페 1차 프로토콜 명시, 테헤란로 허브 표기
- `/onboarding` 스텝 UI (성별 → 존 선택 → 회사 이메일 → AI 인터뷰 → 프로필 확인)
- 이 단계는 화면만. 데이터는 로컬 상태.

### Step 2 — Cloud 활성화 + 계정/인증/스키마
- 이메일+비밀번호 회원가입, `profiles` 자동 생성 트리거
- 스키마: `profiles`, `zones`, `work_verifications`, `affinities`, `intro_queue`, `ticket_ledger`, `meetings`, `feedback`, `user_roles`
- 회사 이메일 인증: 회사 이메일로 6자리 코드 발송 → 검증 시 `work_verified_at` 세팅. 개인 메일 도메인(gmail 등) 차단 목록.
- 모든 테이블 RLS + GRANT. 프로필 사진/상세는 **소개가 열린 쌍**과 **평가 대상**에게만 노출되는 정책.

### Step 3 — AI 인터뷰 프로필
- Lovable AI로 대화형 인터뷰(6~8문항: 일상, 가치관, 갈등 대처, 이상형, 카페/술 선호)
- AI가 소개글·가치관 태그·이상형 요약 초안 생성 → 사용자가 수정 후 확정
- 미완료 시 `profile_status = incomplete` → 매칭 풀 제외

### Step 4 — 여성 평가 화면 + 크레딧
- 같은 존 남성 프로필 1장씩 호/불 (버튼, 스와이프 아님)
- 평가 시 `affinities` 기록 + `credits` 적립, 이미 평가한 상대 재노출 없음

### Step 5 — 남성 소개 티켓 → 순차 1명
- 소개 티켓 사용 → 나에게 like 준 여성 중 1명 `opened` (불변식: 동시 opened ≤ 1)
- 만남 티켓 사용 / 사용 안 함 결정. 미사용 → `passed`, 해당 쌍 영구 재큐잉 금지
- 72h 미결정 시 자동 만료(passed 처리)
- MVP 결제는 미연결: 티켓은 운영자 지급(`source=grant`) + 잔액 UI. 실결제(PG/IAP)는 별도 승인 후.

### Step 6 — 조율 채팅 → 사적 채팅 게이트 → 만남 → 피드백
- 만남 티켓 사용 시 `meetings` 생성, **조율 채널**만 오픈 (날짜·시간·카페 제안/수락 UI 중심)
- 일정 확정 시 `private_chat_opens_at = 만남 전날 00:00` 자동 계산, 일정 변경 시 재계산
- 그 시각 이전에는 사적 채팅 전송 서버단 차단
- 만남 후 피드백 폼 → 여성 `manner_temp` 갱신 (기본 36.5, 항목 평균 기반 ±)

### Step 7 — 퍼널 로깅 + 안전
- 이벤트 로그: 가입→인증→평가→소개오픈→만남티켓→만남완료→피드백 (허브별)
- 신고·차단, 노쇼 신고, 프로토콜 위반 신고

## 기술 메모

- TanStack Start + Lovable Cloud(Postgres/Auth/Storage), 서버 로직은 `createServerFn`
- 상태 전이(intro/meeting)는 전부 서버 함수에서만 수행 — 클라이언트가 상태를 직접 쓰지 못하게 함
- 핵심 불변식은 DB 제약으로도 강제: 남성별 `opened` 유니크 부분 인덱스, `(male_id, female_id)` 유니크
- 사적 채팅 게이트는 UI 숨김이 아니라 **RLS/서버 검증**으로 강제

## 이 계획에 없는 것 (의도적)

그룹 미팅, 전국 매칭, 스와이프 피드, 카페 쿠폰, 사람 컨시어지, 실결제 연동, 소득/자산 뱃지.

## 승인 필요 지점

- 브랜드명 「퇴근길」 확정 여부
- Step 2에서 Cloud(DB·인증·개인정보 보관) 활성화
- Step 5의 티켓 가격·실결제는 별도 대화로 분리
