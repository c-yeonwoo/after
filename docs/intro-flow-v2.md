# 소개 흐름 v2 — 운영자 큐레이션

작성 2026-08-09. **구현 완료 — 2026-08-11.**

구현하면서 설계와 달라진 곳은 각 절에 `구현` 표시로 적어 두었다. 문서를 먼저
읽는 사람이 틀린 전제를 들고 코드를 보지 않도록, 바뀐 이유까지 남긴다.

| 단계 | 마이그레이션 |
|---|---|
| 티켓 종류 | `s19_ticket_kind` |
| 소개 큐 · `open_intro()` 재작성 | `s20_intro_queue` |
| 큐 조회 RPC | `s20b_admin_queue_read` |
| 상점 · 홈 · 열람 확인 (화면만) | `s20c` (커밋) |

기존 흐름(v1)은 여성의 호감이 곧바로 소개가 됐다. v2 는 그 사이에 **운영자
큐레이션**을 넣고, **소개 열람 자체를 유료화**한다.

---

## 1. 무엇이 바뀌나

### v1 (현재)

```
여성이 남성 후보 평가 → like
      ↓ 즉시
남성이 open_intro() → "나를 좋다고 한 여성" 중 가장 오래된 한 명이 열림 (무료)
      ↓
만남 티켓 30,000원 → 주선 시작
```

### v2

```
① 여성이 남성 후보 평가 → like            (변경 없음)
      ↓
② 운영자가 어드민에서 남성을 조회
   → 그를 좋다고 한 여성 카드 리스트를 봄
   → 정렬해서 그 남성의 소개 큐를 만든다     ← 신규
      ↓
③ 남성이 "소개 받기" ON 이고 큐에 카드가 있으면
   → "소개가 도착했습니다"                  ← 전송 시점이 바뀐다
      ↓
④ 소개 프로필 열람 = 소개 티켓 5,000원 1장  ← 신규 유료화
   한 번에 하나만
      ↓
⑤ 만남 티켓 30,000원 → 주선 시작
   또는 패스 → 다음 카드 (또 소개 티켓 필요)
```

### 결정된 것

| | |
|---|---|
| 소개 티켓 | **소멸**. 패스해도 환불 없음, 다음 카드도 5,000원 |
| 큐레이션 | **순수 큐레이션**. 운영자 큐가 비면 소개가 안 나간다(자동 폴백 없음) |
| 판매 | 1장 5,000원 + 번들 병행 (§5) |
| 큐 카드 유효기간 | **전송된 시점부터 3주.** 지나면 만료 — §3-2 `구현` 참고 |
| 소개 받기 OFF | **큐레이션 대상에서 빠진다.** 큐를 쌓아두지 않는다 |
| 남성 토글 | "소개 받기" — **잠시 쉬기를 흡수**한다 |
| 여성 | 기존 "잠시 쉬기" 유지 |
| AI 추천 | 나중. palette 배선을 가져올 예정 — 지금은 수동 정렬만 |

## 2. 먼저 짚어둘 것 — 이건 가격 인상이다

```
v1  만남까지            30,000원
v2  운 좋으면   5,000 + 30,000 = 35,000원
    3명 패스 후 5,000×4 + 30,000 = 50,000원
```

그리고 **5,000원을 내고 열었는데 별로면 그 돈은 그냥 날아간다.**

여기서 나오는 두 가지 압력을 설계가 감당해야 한다.

**① 큐레이션 품질 = CS 부하**
돈을 받고 연 카드가 별로면 그건 곧 환불 요구다. v1 에서는 열람이 무료라 불만이
"소개가 안 온다" 정도였지만, v2 에서는 **"돈 냈는데 이게 뭐냐"** 가 된다.

→ 대시보드에 **패스율**을 넣는다. 특정 운영자·특정 큐의 패스율이 높으면 큐레이션이
   나쁘다는 신호다. 이 숫자가 없으면 품질을 관리할 방법이 없다.

**② 운영자가 매칭의 단일 실패점이 된다**
순수 큐레이션이므로 운영자가 큐를 안 만들면 서비스가 멈춘다.

→ 대시보드에 **적체 지표**를 넣는다. "큐레이션 대기 중인 like 수", "큐가 빈 활성
   남성 수", "가장 오래 기다린 like". 사람이 병목이라는 사실을 숫자로 본다.

## 3. 데이터 모델

### 3-1. 티켓에 종류를 붙인다

```sql
create type ticket_kind as enum ('intro', 'meeting');

alter table tickets add column kind ticket_kind not null default 'meeting';
--  기존 행은 전부 만남 티켓이다. default 로 backfill 되고 그 뒤 default 를 지운다.
```

`price_krw` 는 이미 있다. 종류별 단가 검증은 CHECK 로 묶는다 — v1 에서
`ticket_bundle_amount()` 를 단일 진실로 삼았던 방식을 그대로 이어간다.

### 3-2. 소개 큐

```sql
create table intro_queue (
  id           uuid primary key default gen_random_uuid(),
  male_id      uuid not null references profiles(id) on delete cascade,
  female_id    uuid not null references profiles(id) on delete cascade,
  position     integer not null,              -- 운영자가 정한 순서
  curated_by   uuid not null references profiles(id),
  note         text,                          -- 큐레이션 사유(왜 이 사람을 위에 뒀나)
  delivered_at timestamptz,                   -- 남성 화면에 "도착" 으로 뜬 시각
  expires_at   timestamptz not null,           -- 큐에 담긴 시점 + 3주
  created_at   timestamptz not null default now(),

  unique (male_id, female_id)
);
create index on intro_queue (male_id, position) where delivered_at is null;
create index on intro_queue (expires_at) where delivered_at is null;

--  전송: 미열람 상위 3장만 남성에게 보인다(promote_intro_queue)
--  만료: pg_cron 이 expires_at 지난 미열람 카드를 정리한다(expire_intro_queue_15m)
```

**큐(대기) 와 소개(열림)를 나눈다.** 큐는 운영자 소유이고, `intros` 는 남성이
소개 티켓을 써서 연 결과다. 섞으면 "아직 안 본 것"과 "본 것"의 경계가 흐려진다.

### `구현` 상한을 큐가 아니라 **전송** 기준으로 옮겼다

위 설계는 "미열람 3장" 을 큐 자체의 상한으로 뒀다. 구현에서는 운영자가 미리 긴
줄을 세울 수 있게 하고, 남성에게는 **상위 3장만 전송**하고 나머지는 대기시킨다.
운영자가 한 사람의 큐를 짤 때 3장에서 손을 떼야 하면, 다음에 다시 그 사람을 열어
같은 판단을 반복해야 한다.

그래서 **만료를 큐 진입이 아니라 전송 시점부터 센다.** 담긴 시점부터 3주를 세면
뒤에서 기다리던 카드가 열려보지도 못하고 만료된다 — 큐레이션 노동이 그대로 새는
구조가 된다. `expires_at` 은 `delivered_at` 과 함께 채워지고, 둘 중 하나만 있는
상태는 CHECK 로 막았다.

자리가 비면(열람·패스·만료) 곧바로 뒷줄을 승격시킨다. 승격은 크론이 아니라 큐가
바뀌는 순간마다 부른다 — 방금 세운 줄이 15분 뒤에 닿으면 수동 운영에서 그 지연이
곧 CS 다. 크론은 만료만 맡는다.

남성은 RLS 로 **전송된 카드만** 본다. 대기 중인 뒷줄이 보이면 "몇 명이 나를
좋아하는지" 가 큐레이션 이전에 새어 나간다.

### 3-3. 남성 소개 받기 토글

**새 컬럼을 만들지 않는다.** 기존 `paused_at` 을 그대로 쓴다.

| | `paused_at` 의 의미 | 화면 라벨 |
|---|---|---|
| 남성 | 여성 평가 큐에서 빠짐 **+ 소개 카드가 오지 않음** | **소개 받기** |
| 여성 | 남성에게 소개되지 않음 | **잠시 쉬기** |

남성 쪽에만 "카드 전송 중단" 효과가 하나 더 붙는다. 컬럼을 늘리면 두 상태가
어긋날 수 있는데(노출은 켜고 수신은 끈 상태 등) 그런 조합에 제품적 의미가 없다.

## 4. 함수

### 운영자

```sql
-- 이 남성을 좋다고 한 여성들 (아직 큐에 없고, 배제되지 않은)
admin_like_pool(p_male uuid) → table(...)

-- 큐를 통째로 설정한다(순서 포함). 부분 수정이 아니라 덮어쓰기 —
-- 순서 재배열이 잦을 것이므로 부분 갱신보다 단순하다.
admin_set_queue(p_male uuid, p_female_ids uuid[], p_note text) → integer

-- `구현` 추가된 것
admin_curation_targets() → table(...)   -- 작업 대상 목록. 큐 빈 사람부터
admin_queue(p_male uuid) → table(...)   -- 이 남성의 미열람 큐
promote_intro_queue(p_male uuid)        -- 내부. 상위 3장을 전송 상태로
expire_intro_queue()                    -- service_role. 3주 미열람 정리 + 승격
```

`admin_*` 는 전부 `is_admin()` 를 통과해야 하고 `admin_actions` 에 기록한다.

**`구현`** `admin_like_pool` 이 `setof public_profiles` 가 아니라 자체 컬럼을
낸다. `public_profiles` 는 호출자 기준 뷰라 운영자에게는 자기 것만 보인다.
같은 이유로 큐 조회도 PostgREST 임베드가 아니라 `admin_queue()` RPC 다 —
임베드는 조인 대상(`profiles`)의 RLS 를 그대로 타서 이름이 `null` 로 온다.

**`구현`** `admin_set_queue` 는 호감 풀에 없는 사람을 거절한다. 화면을 우회해
임의의 여성을 큐에 밀어 넣을 수 없다 — 아래 불변식이 서버에서 지켜져야 한다.

### 사용자

```sql
-- 큐에서 다음 카드를 연다. **소개 티켓 1장을 차감한다.**
--   · 이미 열려 있고 미결정인 소개가 있으면 그것을 반환(불변식 2 유지)
--   · 큐가 비었으면 P0002
--   · 소개 티켓이 없으면 P0003   ← `구현` 에서 정한 코드
open_intro() → intros          -- 재작성

-- 현재 소개를 패스. 소개 티켓은 환불하지 않는다.
pass_intro() → void            -- 기존 유지 + 큐에서 제거
```

**`open_intro()` 의 불변식은 유지된다** — 큐는 `admin_like_pool()` 로만 만들 수
있고, 그 풀은 "나를 좋다고 한 여성" 이다. 화면의 *"이분이 먼저 회원님을 좋다고
하셨어요"* 는 여전히 참이다.

## 5. 가격

```sql
intro_ticket_bundles()     1장  5,000  /  5장 22,000
meeting_ticket_bundles()   1장 30,000  /  3장 85,000                    (유지)
```

### 시장 위치

경쟁 서비스는 소개권 1개 25,000원 · 만남권 1개 100,000원 수준이다. 우리는 각각
**1/5, 1/3** 이다. 저가로 승부하는 포지션이다.

### 번들은 두 개다

```
1장  5,000원  → 장당 5,000원
5장 22,000원  → 장당 4,400원   (12% 할인)
```

10장 번들은 **뺐다.** 44,000원이면 장당 4,400원으로 5장과 같아서, 5장을 두 번
사는 것과 값이 똑같고 소진 부담만 컸다 — 살 이유가 없는 상품이었다.

### 단위 경제 — 저가 승부의 진짜 제약

**큐레이션 노동은 선불이고, 수익은 후불이며 확률적이다.**

운영자가 남성 한 명의 큐를 짜는 데 드는 시간은 확정 비용이다. 그런데 수익은 그
남성이 카드를 **열어야** 발생한다. 안 열면 그 노동은 회수되지 않는다.

경쟁사가 25,000원을 받는 건 그만큼 한 건에 공들일 여력이 있다는 뜻이기도 하다.
5,000원에 사람 손 큐레이션을 붙이면 **처리량으로만 버틸 수 있고, 운영자 1명이
감당 가능한 건수가 곧 서비스 상한이 된다.**

→ 그래서 대시보드의 **"큐레이션 → 열람 전환율"은 품질 지표가 아니라 단위 경제
   지표다.** 이게 낮으면 큐레이션 노동이 새고 있다는 뜻이다.

**`구현`** `admin_dashboard()` 의 `quality` 묶음에 세 값을 넣었다 —
`cards_delivered`(전송) · `cards_opened`(열람) · `cards_expired`(만료). 앞의 둘이
전환율의 분모·분자이고, 만료는 헛돈 노동의 양이다. 적체 쪽에는
`starved_males`(큐가 비어 지금 아무것도 못 받는 활성 남성)를 더했다 — 순수
큐레이션에서 이 숫자가 곧 멈춰 있는 사용자 수다.

## 6. 화면 변경

| 화면 | 변경 |
|---|---|
| 홈(남성) | "소개가 도착했습니다" 는 **큐에 카드가 있을 때** 뜬다. 없으면 대기 |
| 소개 상세 | 열람 전에 **"소개 티켓 1장을 사용합니다"** 확인. 열람 후 만남/패스 |
| 티켓 상점 | **소개 티켓 / 만남 티켓 두 종류.** 보유 현황도 둘 다 |
| 환경설정(남성) | **소개 받기** 토글 (잠시 쉬기 대체) |
| 환경설정(여성) | 잠시 쉬기 (변경 없음) |
| 어드민 | 큐레이션 탭: 작업 대상 목록 → like 풀 → 큐 편집(순서·사유) |

**용어를 갈라야 한다.** 지금은 "티켓"이 하나뿐이라 그냥 티켓이라 부르지만, 둘이
되면 화면마다 어느 티켓인지 분명해야 한다.

**`구현`** `MEETING_TICKET_PRICE_*` 는 이미 종류가 붙은 이름이라 그대로 두고
`INTRO_TICKET_PRICE_*` 를 나란히 추가했다. 상점은 종류 탭으로 갈랐고, 약관 문구도
종류별로 다르다 — 소개 티켓은 **소멸** 이고 만남 티켓은 조건부 환불이라 같은
문장을 쓸 수 없다. 소개 화면의 열람 버튼은 큐·티켓 상태에 따라 세 갈래다
(열기 / 상점으로 / 대기).

## 7. 무엇이 깨졌나 `구현`

예상한 것과 실제로 깨진 것을 함께 남긴다 — 다음에 티켓·소개 흐름을 건드릴 사람이
같은 자리를 다시 밟는다.

| 대상 | 결과 |
|---|---|
| `open_intro()` | 재작성. 큐에서 꺼내고 소개 티켓을 차감한다 |
| `home_state()` | `queued_intros` · `intro_tickets` · `meeting_tickets` 추가 |
| `next_candidate()` | 변경 없음 (여성 평가 큐는 그대로) |
| `use_meeting_ticket()` | `kind = 'meeting'` 필터 추가 — **예상대로 가장 위험한 지점이었다** |
| `refund_ticket()` | 소개 티켓이면 거절한다(소멸) |
| pgTAP | `open_intro` 를 검사하는 **6개 파일 10개 지점** 에 큐 카드 + 소개 티켓 전제를 넣었다 |
| 상점·홈·소개 화면 | §6 |

### 예상하지 못했던 것 네 가지

**① 인자를 늘리면 새 함수가 생긴다.** `create or replace` 가 아니다. 구 시그니처를
남긴 탓에 `ticket_bundles` · `issue_ticket` · `create_ticket_order` 가 차례로
`function is not unique` 로 깨졌다 — 상점 화면과 pgTAP 이 함께 죽었다. 인자를
늘릴 때는 구 시그니처를 반드시 함께 `drop` 한다.

**② 노쇼 보상 발급이 막혔다.** `tickets.kind` 의 default 를 지우자
`apply_no_show_confirmed` 의 insert 가 not-null 위반이 났고, 그 티켓은 0원이라
금액 띠 CHECK 에도 걸렸다. `tickets` 에 넣는 **모든** 경로를 세어야 한다(당시 3곳).

**③ 소개를 먼저 만들고 티켓을 붙여야 한다.** `tickets_check2` 가
`used → intro_id is not null` 을 요구한다(s1). 티켓을 먼저 `used` 로 바꾸면 제약에
걸린다. 순서를 뒤집으면 "이 소개 티켓이 어느 소개를 열었나" 가 행에 남아 정산도
추적된다.

**④ 화면이 진입만으로 돈을 쓰고 있었다.** v1 의 `open_intro()` 는 공짜였으므로
홈과 소개 탭이 진입 시 **자동으로** 불러줬다. 유료화하면 탭을 여는 것만으로
5,000원이 빠진다. 두 곳의 자동 호출을 걷어내고 확인 버튼으로 옮겼다. 무료였던
호출을 유료로 바꿀 때는 **호출부를 먼저 세어야 한다.**

## 8. 만료 처리 — 정해서 구현했다 `구현`

**남성에게는 조용히, 운영자에게는 숫자로.** 아직 열지 않은 카드가 사라지는 것이라
남성 입장에서는 잃은 것이 없다. 반대로 "소개가 만료됐습니다" 는 하지 않은 일에
대한 부정적 통지라 얻는 게 없다.

운영자 쪽은 다르다. 만료 건수는 **큐레이션이 헛돌았다는 신호**이므로 대시보드
품질 묶음에 남긴다 — §2·§5 의 단위 경제와 직결된다.

`expire_intro_queue_15m` 이 다섯 번째 pg_cron 잡으로 붙었다. 만료된 카드를 지우고
`intro_queue_expired` 이벤트를 남기고, 빈 자리에 뒷줄을 승격시킨다.

### 아직 안 정한 것

**소개 티켓 만료** — 지금은 만료되지 않는다(상점 약관에 그렇게 적었다). 큐 카드는
3주면 사라지는데 티켓은 남으므로, 티켓을 사두고 카드가 만료되는 조합이 반복되면
"돈만 내고 못 봤다" 는 CS 가 된다. 실사용 데이터를 보고 정한다.

**큐레이터별 패스율** — s22 에서 붙였다. 대시보드 아래 표. 자세한 것은
[`admin-design.md`](./admin-design.md) §4.

구현하며 알게 된 것: **intro_queue 만으로는 퍼널을 셀 수 없다.** 패스와 만료가
큐 행을 지우기 때문에 살아남은 행으로 세면 담은 수가 줄고 패스는 0 이 된다.
열린 카드의 내구성 있는 기록은 `intros` 이므로 그 행에 `curated_by` 를 새겼고,
카드를 대기(큐)·열림(intros)·만료(events) 세 갈래로 나눠 정확히 한 번씩 센다.
