# 애프터 제품과 1인 운영 통합 설계

작성일: 2026-10-16 · 기준 코드: `ae77e1e` · 상태: **설계안 작성 완료, 구현 승인 전**

애프터의 경쟁력은 많은 프로필이나 AI 자체가 아니라, **퇴근 동선이 맞는 직장인의 탐색·조율 부담을 줄여 실제 약속으로 연결하는 것**이다. 이를 위해 사용자 화면, 소개 자격, 운영 작업함, 자동화, 측정 지표가 같은 상태를 바라보도록 한다.

이번 변경은 설계 문서만이다. 제품 코드·DB·운영 설정은 바꾸지 않는다. 기존 가격, 남녀 소개 방식, 티켓 정책도 이 설계만으로 변경하지 않는다. `HANDOFF.md`는 갱신하지 않는다.

## 문서 구성

- 이 문서: 제품 전략, 현황 근거, 사용자 플로우, AI·안전·성장 설계와 결정 목록.
- [운영 콘솔 상세 설계](./operations-console-spec.md): IA, 화면, 작업함, 자동화, 지표, 1인 운영 루틴.
- [기술 설계와 구현 계획](./product-operations-implementation.md): 데이터·API 계약, 정합성, 테스트, PR 순서, 출시 게이트.

이 설계가 승인되면 해당 범위의 후속 구현 기준으로 사용한다. 과거 PRD·운영 문서의 가격·디자인·알림 설명을 그대로 최신 사실로 간주하지 않는다. 현재 기능의 근거는 아래 코드이며, 새 정책은 별도로 승인한다.

## 3. 제품 약속과 범위

### 3.1 지킬 약속

- **회사 이메일 소유 확인을 마친 직장인 대상**: 회사 메일 확인을 실재직·소득·직급 보증으로 과장하지 않는다.
- **확인 가능한 소개**: 본인 입력, 인증 결과, 운영자 작성, AI 초안의 출처를 구분한다. 생활·성격의 진실성을 전부 보증하지 않는다.
- **약속 조율 지원**: 권역과 실제 가능한 날짜를 기준으로 연결하고, 막힌 단계는 운영자가 확인한다.
- **불발 시 정해진 조건의 만남 티켓 반환**: 현금 환불과 구분한다. 무조건적인 만남·연애 성사 보장 문구는 사용하지 않는다.

핵심 카피 후보: **“퇴근 후, 약속 하나.”** 보조 설명: “가까운 직장인을 소개하고, 만날 시간을 함께 정해요.” 인증 범위와 티켓 조건은 관련 화면에서 구체적으로 보여준다.

### 3.2 유지할 것과 하지 않을 것

유지: 여성 후보 확인→호감→운영자 검토→남성 소개 열람→만남 요청 흐름. 소개/만남 티켓 구분, 현재 판매 가격, 신규 티켓 12개월 및 반환 티켓의 원래 만료일 유지, 기존 무료 티켓의 예외. 반환과 유료 결제 취소의 정확한 자격은 기존 서버 규칙 및 별도 법률 검토로 확정한다.

이번에 하지 않음: 남녀 가격 재설계, 무제한 무료 혜택 확정, 궁합 점수, 외모·직장 서열, LLM 자동 매칭/제재/환불, DM 영업, 사용자 원문을 외부 스킬에 전송, 대규모 데이터 웨어하우스, 새 마이크로서비스, 운영 핵심 로직의 Make/n8n 이관.

## 4. 사용자 상태와 행동 설계

### 4.1 표시 상태의 원칙

`onboarding_step=7`은 입력 완료일 뿐 소개 자격 충족과 동일하지 않다. 서버가 `primary_state`, `blockers[]`, `next_action`, `deadline_at`, `as_of`를 반환한다. 공개용 상태에 운영 메모나 다른 회원의 거절 사유를 넣지 않는다.

독립적인 네 축을 유지한다: 계정/안전, 소개 자격, 소개·약속 진행, 거래. 이들을 하나의 거대한 enum으로 합치지 않는다. 홈의 주 행동만 우선순위로 결정한다.

우선순위: 접근 제한 안내 → 기한 있는 신고 응답/다가오는 약속의 필수 안내 → 자격 보완 → 진행 중 약속 행동 → 열린 소개 → 소개 도착 → 휴식 → 준비/공급 대기. 자격 변경 때문에 기존 약속 조회·취소·문의까지 막지 않는다. 기존 만남과 새 소개 권한은 별도다.

| 상황                   | 화면 문구 예시                  | 주 행동                  | 운영 연계                                |
| ---------------------- | ------------------------------- | ------------------------ | ---------------------------------------- |
| 입력 미완료            | 소개받을 준비를 마저 해주세요   | 이어서 작성              | 미완료 단계 관측, 임의 재초대 없음       |
| 인증 필요              | 본인 확인이 필요해요            | 인증하기                 | 공급자 오류·재시도 초과만 작업 생성      |
| 사진 검수 중           | 사진을 확인하고 있어요          | 없음, 프로필 수정은 보조 | 검수 대기와 기한 초과                    |
| 사진 반려              | 사진을 다시 올려주세요          | 사진 변경                | 반려 사유와 기준 표시                    |
| 여성, 후보 있음        | 살펴볼 소개가 있어요            | 소개 보기                | 노출·호감 기록                           |
| 여성, 호감 후 대기     | 새로운 소식이 오면 알려드릴게요 | 다른 소개 보기(있을 때)  | 호감→전송·열람·요청 적체를 내부에서 구분 |
| 남성, 준비 완료·미도착 | 소개를 준비하고 있어요          | 없음                     | 운영 미처리/후보 부족을 구분             |
| 남성, 소개 도착        | 소개가 도착했어요               | 소개 확인                | 차감 전 티저·비용·만료 안내              |
| 요청 수신              | 만날 시간을 골라주세요          | 요청 확인                | 응답 기한과 전송 가능 채널 확인          |
| 요청 발신              | 상대의 답변을 기다리고 있어요   | 요청 상세                | 기한 경과 시 기존 반환 규칙 실행         |
| 일정 재조율            | 가능한 날짜를 확인해주세요      | 일정 확인                | 48시간 정체 시 운영 개입                 |
| 약속 확정              | 만남이 잡혔어요                 | 약속 확인                | 날짜·장소·지도·변경/취소 접근            |
| 만남 후                | 만나보셨나요?                   | 만남 결과 남기기         | 한쪽 응답과 양측 확인을 구분             |
| 휴식                   | 소개를 잠시 쉬고 있어요         | 소개 다시 받기           | 신규 노출 중지, 진행 중 약속은 유지      |
| 장애                   | 지금 상태를 불러오지 못했어요   | 다시 확인                | 이전 성공 데이터 시각, 오류 ID           |

사용자에게 운영팀의 다음 확인일을 표시하려면 실제 작업의 `due_at`과 연결해야 한다. 예측 근거가 없으면 “곧”, “오늘”, “3일 안” 같은 약속을 생성하지 않는다. 후보 부족을 “운영자가 준비 중”으로 무기한 포장하지 않는다. 장기 대기에는 “현재 조건에 맞는 소개가 부족해요”와 쉬기·문의 선택지를 제공한다.

### 4.2 핵심 여정의 변경

1. **가입**: 로그인/시작하기는 같은 계정 진입 후 서버 상태로 분기. 입력 저장, 인증 취소 복귀, AI 실패 시 직접 작성 제공. 준비 완료와 검수 중을 구분한다.
2. **소개**: 티저의 공개 범위 유지. 한 번의 명시적 확인으로만 티켓 사용. 홈 조회·새로고침·뒤로가기로 차감하지 않는다.
3. **일정**: 현재 서버의 평일 저녁 슬롯·1~3안·21일 범위를 기준으로 화면과 문서 통일. 상대 수락 직전 유효성·중복 약속을 재확인한다. 충돌 판단은 슬롯 점유 범위의 승인된 정책을 적용한다.
4. **변경/취소**: 사유, 상대 통지, 티켓 영향, 되돌릴 수 있는 범위를 확인 화면에 표시. 응답 없는 날에는 다른 날을 자동 확정하지 않는다.
5. **만남 후**: 실제 만남 여부→간단한 경험 질문 순서. 후기 공개·홍보 활용은 별도 선택이며 긍정 후기 강요나 공개 후기와 보상 묶기는 하지 않는다.
6. **문의/신고/탈퇴**: 어떤 화면에서도 찾을 수 있게 유지. 일반 문의와 안전 신고의 처리 흐름을 분리하고, 정지 회원도 이의 제기 경로는 유지한다.

## 5. 디자인과 사용자 인지

Emil의 위계·절제·반복 작업 속도 원칙을 적용한다. 모바일는 `mobile-native`의 입력 크기·안전 영역·키보드·터치 기준을 검증 항목으로 채택한다.

| Before                              | After                                           | Why                                            |
| ----------------------------------- | ----------------------------------------------- | ---------------------------------------------- |
| 운영 홈의 업무 종류별 카드 나열     | 상단 상황 요약 + 건별 우선순위 목록 + 상세 패널 | 숫자를 해석하고 대상자를 다시 찾는 작업 제거   |
| 오류가 로딩 상태에 가려짐           | 부분 오류·재시도·마지막 성공 시각               | 정상과 관측 불가를 구별                        |
| 상태·설명·행동이 서로 다른 기준     | 서버 상태에 연결된 한 문장과 한 CTA             | 사용자가 이유와 다음 행동을 추측하지 않게 함   |
| 모바일에서 모든 운영 메뉴 가로 나열 | 오늘/회원/더보기, 긴 목록은 모바일 행 카드      | 빈번한 업무 접근과 터치 가독성 확보            |
| AI 생성문만 표시                    | 원문 근거와 수정/채택 선택                      | 매끄러운 문장을 사실 확인으로 오인하지 않게 함 |

색상은 새로 만들지 않는다. Ink/Paper 기본, Pine은 완료·안정, Coral은 작은 강조, 위험은 기존 destructive 토큰. 상태는 색뿐 아니라 라벨·아이콘으로 표시한다. 어드민 본문 14~16px, 모바일 입력 16px 이상, 주요 터치 영역 44px 이상을 목표로 한다. 업무 목록 정렬/키보드 이동에는 장식 애니메이션을 넣지 않는다. 포커스 복귀, 스크린리더 상태 알림, 축소 모션, 200% 확대를 완료 조건으로 둔다.

사용자 홈에는 대시보드, 궁합 점수, 긴 진행 설명을 추가하지 않는다. 상세 조건·반환 정책은 필요한 결정을 하는 순간 제공한다.

## 6. AI 설계

### 역할과 경계

| 기능               | 입력                          | 출력                                            | 공개/실행 조건                                          |
| ------------------ | ----------------------------- | ----------------------------------------------- | ------------------------------------------------------- |
| 소개글 편집        | 허용된 인터뷰 답·키워드       | 소개글·헤드라인 초안                            | 회원이 확인·수정 후 저장                                |
| 페어 브리프        | 두 회원의 허용된 원문 필드    | 근거 있는 공통점 최대 3개, 대화 주제, 확인할 점 | 운영자 전용. 소개 결정·순위·확률 생성 금지              |
| 문의 답변 보조(P1) | 승인 FAQ와 최소화된 해당 문의 | 근거 문서가 연결된 답변 초안                    | 운영자 승인 후 전송. 결제·안전 판정은 작성하지 않음     |
| 운영 요약          | 집계 수치·작업 유형           | 선택적 일일 요약                                | 숫자는 서버에서 계산, LLM이 건수나 기한을 추정하지 않음 |

먼저 규칙 기반 요약과 답변 템플릿을 구현한다. LLM 호출은 원문 편집이 필요한 곳에 한정한다. 모델명 변경은 이번 설계에서 확정하지 않고 동일 평가셋의 품질·지연·비용 비교로 결정한다.

### 품질과 비용 계약

- 초안은 `source_revision/hash + feature + prompt_version + model`로 식별한다. 원문 변경 시 오래된 초안임을 표시하고 재사용하지 않는다.
- 동일 요청 중복 실행은 서버의 실행 예약·일일 예산으로 막는다. 현재의 실행 이력 count 검사만으로 동시 호출 한도를 보장한다고 보지 않는다.
- 브리프의 근거는 `source_field`, 짧은 원문 인용, 해당 사용자 참조로 구조화. 문자열 존재 검증과 의미 검토를 함께 하고, 근거 없음은 표시하지 않는다.
- AI 결과에 대한 채택/수정/폐기와 폐기 이유를 기록한다. 프로필·대화 원문을 `ai_runs`나 일반 분석 로그에 복사하지 않는다.
- 전화·메일·실명·사진·신고/대화 원문은 기본 입력 제외. 자유 입력에 사용자가 적은 연락처도 외부 전송 전 마스킹한다.
- 실패·거절·타임아웃은 직접 작성 또는 원 프로필 비교로 진행. AI 장애가 소개나 운영 전체를 막지 않게 한다.
- 일 예산은 설정값으로 두고 금액은 실제 공급자 가격표 버전을 기록해 산정한다. 가격 미설정은 0원이 아니라 비용 미산정이다.

평가셋은 합성/허가된 최소 데이터로 구성한다. 원문 없는 사실 생성, 상충 정보, 인젝션, 연락처 포함, 공통점 없음, 짧은 답, 과장 문구, 프로필 수정 후 캐시를 포함한다. 현재 형식 검사 38건을 유지하되 이를 사실성 검증 완료로 부르지 않는다. 고위험 사실 창작 0건을 출시 게이트로 하고, 유용성·자연스러움은 운영자 블라인드 평가와 실사용 수정률로 확인한다.

## 7. 안전·개인정보·거래

- 성인 확인은 통신사 인증의 서버 검증 결과가 권위다. 자체 문자 OTP·자가 생년월일과 같은 배지로 표시하지 않는다. 계약·실인증·플래그 활성화는 각각 별도 증빙이다.
- 제재는 근거·양측 진술·담당자·사유를 기록하고 이의 제기를 연결한다. AI나 무응답만으로 영구 제재하지 않는다.
- 운영자 민감 조치는 강화 인증과 서버 권한을 요구한다. MFA 도입 시 예비 복구 수단을 먼저 준비하여 유일한 운영자가 잠기지 않게 한다.
- 알림 잠금화면은 상대 이름·데이팅 활동의 상세 노출을 기본값으로 삼지 않는다. 일반 문구와 로그인 후 상세 조회를 사용한다.
- 개인정보 보유·삭제·처리자·국외 이전은 실제 흐름과 대조한다. 새 작업 메모·AI 초안·문의 이력도 탈퇴 전파 대상에 포함한다.
- 재동의는 정책 버전·발효일·변경 범위에 따라 서버에서 요구한다. 동의 거절 시 새 소개/구매는 제한하되 보유 권리·문의·취소·탈퇴 경로를 없애지 않는다.
- 환불 불가를 일괄 적용하지 않는다. 기존 반환·결제 취소 코드와 공개 약관을 대조하고 법률 검토 결과로 확정한다. 설계 문서는 법률 의견이나 심사 통과 증빙이 아니다.

## 8. 모집·수급·수익 설계

### 모집 기준

광고 목표는 단순 회원 가입이 아니라 **동일 퇴근권의 소개 자격 충족자 확보**다. 광고→랜딩→가입→자격 충족→소개→만남을 캠페인 ID로 연결하되, 성향·프로필·신고 정보는 광고 도구로 보내지 않는다.

초기 모집은 작은 기수 단위로 운영하는 방식을 권고한다. 정확한 인원·무료 티켓 수·마감일은 대표가 승인한 설정으로만 공개한다. 자동화는 부족 집단/권역과 처리 여력을 추천하며 광고 예산·모집 중지·가격은 자동 변경하지 않는다.

모집 과잉 경보는 성비 하나가 아니라 권역별 실제 후보 간 연결 가능성, 최근 활동, 대기 나이, 운영 적체를 같이 본다. 재직·연령·민감 특성을 차별적 점수나 광고 타깃 자동화에 사용하지 않는다.

### 기다리는 시간과 운영 용량

- 남성: 자격 충족→첫 노출→첫 호감→소개 전송→열람→약속 확정.
- 여성: 자격 충족→후보 노출→호감→소개 전송/열람→만남 요청→약속 확정.
- 양측: 진행 중인 각 단계의 대기 나이와 완료된 단계의 소요시간을 분리. 휴식 시간을 뺀 활성 대기와 달력 시간을 함께 정의한다.
- 모집 초기에는 예측 숫자를 약속하지 않는다. 표본·미완료 비율·관측 기간을 먼저 표시한다. 세그먼트 완료 표본 30건 미만이면 p90 기반 대외 예측을 숨기는 것을 초기 기준으로 제안한다.

운영 용량은 `일일 가용 분 × 0.7 / 실측 건당 처리 분`으로 계획한다(30%는 문의·사고 버퍼, 제안값). 예: 60분·건당 5분이면 약 8건/일이지 12건을 전부 신규 소개에 쓰지 않는다. 이 숫자는 실제 처리량 예측이 아니라 가정 예시다. 운영 2주 후 측정값으로 바꾼다.

공헌이익은 실제 수납액에서 취소액·PG·본인확인·AI·통신·운영 시간 원가를 빼서 본다. 무료 베타는 매출과 유료 구매 의사 검증을 대신하지 않는다. 티켓 반환을 현금 환불이나 신규 매출로 중복 계산하지 않는다.

## 9. 사용자 검증 계획

모집 대상: 강남·역삼 퇴근권 직장인, 남녀 흐름 모두 포함. 목표는 통계적 대표성이 아니라 치명적 오해 발견이다.
