## 문제

기존 데이팅 앱은 무제한 스와이프로 만남을 가볍게 만들고, 하이엔드 검증 앱은 계급 프레임으로 진입 장벽을 만들고, 결혼정보회사는 무겁고 비싸다.

대상 사용자는 **진지한 만남을 원하고 비용도 낼 의향이 있지만, 스펙 비교와 무한 탐색에 지쳐 있다.** 동시에 현실적으로 **시간·거리·신뢰**가 필요하다.

풀려는 것: **같은 퇴근권에서 신뢰가 확보된 직장인끼리, 한 번에 한 사람만 소개받아, 퇴근 후 한 번 실제로 만나게 한다.**

## 대상 사용자와 시나리오

| 역할 | 페르소나                           | 동기                                                    | 지불               |
| ---- | ---------------------------------- | ------------------------------------------------------- | ------------------ |
| 여성 | 강남·역삼권 직장인, 20대 후반~30대 | 스펙 쇼핑 없이 퇴근 후 부담 없는 한 번의 만남           | 무료               |
| 남성 | 동일 권역 직장인                   | 이미 호감을 준 상대만 순차로, 시간·비용을 아껴 만남까지 | 만남 티켓 30,000원 |

### 핵심 시나리오 (해피패스)

1. 가입 → 퇴근권 선택 + **회사 이메일 인증** → **인터뷰로 프로필 생성**
2. 여성이 같은 권역 남성 프로필을 **무료로** 호·불 평가
3. 남성에게 **자신에게 호감을 준 여성 중 1명**이 순차로 공개
4. 남성이 **만남 티켓(30,000원)** 사용 여부 결정
5. 사용 시 → 상대에게 가능한 날짜·지역 선호를 물어 정리
6. 양쪽 확인 후 **조율 채팅** 오픈 → 날짜·장소 확정
7. **확정 시점 기준으로 사적 채팅** 오픈 (§미해결 Q2)
8. 만남 → **"만났어요" 확인** → 피드백(선택)

## 목표 (성공 지표)

런칭 전이므로 **계측 자체가 목표의 일부다.** 현재 애널리틱스 이벤트는 0건이고, 피드백 제출은 저장조차 되지 않는다.

**북극성: 주간 실제 1차 만남 완료 수 (권역별)**

베타 표본이 작으므로 **비율이 아니라 절대 개수와 사용자별 타임라인으로 읽는다.** 표본이 작을 때 전환율은 무정보에 가깝다.

### 최소 이벤트 8개 (F10)

`signup_verified` · `profile_completed` · `affinity_submitted` · `intro_opened` · `intro_passed` · `ticket_purchased` · `meeting_confirmed(place_kind)` · `meeting_completed`

### 추적 지표

| 지표               | 정의                           | 왜                                               |
| ------------------ | ------------------------------ | ------------------------------------------------ |
| 권역 밀도          | 주간 활성 여·남 수             | 최대 리스크(콜드스타트). 임계 미달 시 소개 중단  |
| 여성 평가 참여     | 주간 호·불 수 / 활성 여성      | 남성 소개 큐의 공급원                            |
| 소개→티켓 전환     | 소개 오픈 대비 티켓 사용률     | 낮으면 소개 품질 또는 가격 재검토                |
| 티켓→만남 완료     | 티켓 사용 대비 실제 만남 확인  | 노쇼와 함께 추적                                 |
| **장소 종류 분포** | `meeting_confirmed.place_kind` | **제한하지 않지만 관측한다.** 아래 리스크 검증용 |
| D7 재방문          | 가입 후 7일 내 재방문          |                                                  |

### 추적해야 할 리스크 (D5 폐기의 부작용)

장소를 자유화하면 **1차 비용이 티켓 가격을 넘어설 수 있다.** 그러면 남성의 선별 기준이 "결이 맞는가"에서 **"이 총지출만큼의 값인가"**로 이동하고, 이는 PRD가 반대해 온 상품화다. 여성 측에는 부담 증가로 수락률이 떨어질 수 있다.

→ **제품은 제한하지 않되, `place_kind`와 티켓→만남 완료율을 함께 본다.** 티켓 사용률이 높은데 만남 완료율이 낮거나, 특정 `place_kind`에서만 취소가 몰리면 그때 가이드(예산 범위 제시)를 도입한다. **지금은 도입하지 않는다.**

## 비목표 (Non-goals)

**MVP에서 하지 않는다:**

- **장소·음식·예산 제한** (폐기된 D5). 추천만 제공하고 강제하지 않는다
- **예약 대행** — 세라는 조율을 돕는 기능이며 예약을 잡지 않는다
- 무제한·일일 N장 **스와이프 피드**
- **2:2 / 3:3 그룹 미팅**
- **전국 매칭** — 강남·역삼권 단일 권역으로 시작
- **소개 티켓** (만남 티켓과 별개의 두 번째 화폐). 화폐는 하나다
- **여성 크레딧 적립 · 매너온도 · 사진 진위 검증**
- **계급·클럽·상위 1% 브랜딩** (D8 유지)
- **"만남 보장"** 표현. 절대어 대신 환불 규칙을 명시한다
- **"AI" 인터뷰** 표기
- **다크모드** (현재 토글이 없어 사용자에게 노출되지 않음)
- **웹뷰 하이브리드 앱** — 결제 정책 확인 후. 베타는 모바일 웹
- 인간 컨시어지 상주

## 요구사항

### 기능

#### F1. 가입 · 퇴근권 · 직장 인증

- 권역 선택 (강남·역삼권만 `available`, 나머지는 준비 중 표기)
- **회사 이메일 인증** — 개인 메일 도메인 차단 목록은 현재 `isCompanyEmail`에 있으나 **차단 목록은 인증이 아니다.** 실제 메일 발송·토큰 검증이 필요하다
- 성별은 가입 후 변경 불가 (이미 구현)
- **온보딩 진행 상태를 단계별로 저장한다.** 현재 완료 시점에만 저장돼 중간 이탈 시 7단계를 전부 재입력한다

#### F2. 인터뷰 프로필

- 기본 정보(이름·생년월일·직업·사진 1장) + 생활 정보 + 관심사 + 이상형 태그 + 나누고 싶은 주제
- 관심사 입력에 따라 후속 질문이 달라지는 적응형 인터뷰
- 결과로 **한 줄 소개**를 생성하고 사용자가 확인·수정한다
- **표기는 "인터뷰"** — "AI"를 쓰지 않는다

#### F3. 여성 호·불 평가 (무료)

- 같은/인접 권역 남성 프로필을 무료로 평가
- 평가 결과는 상대에게 즉시 노출되지 않는다

#### F4. 소개 오픈 — 한 번에 한 명

- **불변식 1**: 남성에게 공개되는 대상 ⊆ 그 남성에게 호감을 준 여성
- **불변식 2**: 동시 오픈 소개 ≤ 1
- 소개 화면 순서: **사진(한 줄 소개 오버레이) → 기본 정보 → 소개글 → 인터뷰 → 태그**
  - 한 줄 소개를 히어로에 얹어 **"결"이 먼저 읽히게** 한다 (브랜드: 스펙 대신 결)
  - 기본 정보(직업·지역·MBTI·흡연·음주·종교)는 사진 바로 아래에 **펼친 채로** 둔다
  - _개정 이력: 초안은 "스펙은 접어서 아래에"였으나, 실제 화면 검토 후 변경했다.
    직업·지역은 "만날 수 있는 사람인가"를 판단하는 실용 정보라 탭 한 번을 요구할
    이유가 없고, 한 줄 소개가 이미 히어로에 있어 위계 목적은 그대로 달성된다._

#### F5. 만남 티켓 — 30,000원

- 결제 후 티켓 1장 발급, 사용 시 1장 차감
- **차감은 원자적이어야 한다** (§비기능)
- 화면에 **가격을 명시한다.** 현재 가격 문자열이 코드 전체에 0건이다
- **환불 규칙을 문구로 명시한다** (§미해결 Q3)
- "만남 보장" 표현을 쓰지 않는다

#### F6. 조율 — 세라는 "기능"이다

- 티켓 사용 시 상대에게 가능한 날짜·선호 지역을 묻고 정리해 전달
- **장소는 추천 목록으로 제시한다.** 종류·예산을 제한하지 않고, `상관없어요`를 포함한다
- **예약은 하지 않는다.** 화면 문구가 예약 대행을 약속하지 않도록 한다
- 세라의 정체를 **결제 전에 한 문장으로 밝힌다** (예: 자동 안내 기능임을 명시)

#### F7. 채팅 게이트 (D4)

- **조율 채팅**: 날짜·장소를 정하는 데 필요한 범위
- **사적 채팅**: 만남 확정 후 지정 시각에 오픈 (§미해결 Q2)
- 게이트는 **서버가 판정한다.** 클라이언트 상태로 열리지 않는다

#### F8. 만남 확정 · 완료 확인

- 날짜·장소 확정 시 `meeting_confirmed`를 기록하고 `place_kind`를 함께 남긴다
- 만남 후 **"만났어요" 1탭 확인** — 북극성의 유일한 입력이므로 필수
- **완료를 담을 스키마 필드를 신설한다.** 현재 없다

#### F9. 피드백 (선택)

- 상대에게 공개되지 않음
- **실제로 저장한다.** 현재 토스트만 띄우고 저장하지 않는다

#### F10. 계측

- 위 8개 이벤트 발화
- 6개 지표 중 넷은 상태를 서버로 옮기면 이벤트 없이 도출된다. 이벤트는 **이탈·재방문**과 `place_kind`용

### 비기능

#### N1. 서버 권위 — 최우선

현재 티켓·채팅 게이트·역할 검사가 **전부 클라이언트에 있고 두 경로로 뚫린다.** 이 구조를 그대로 Supabase로 옮기면 실제 취약점이 된다.

| 연산               | 클라이언트를 믿어도 되나 | 강제 수단                                                                |
| ------------------ | ------------------------ | ------------------------------------------------------------------------ |
| 티켓 차감          | **아니오**               | Postgres 함수 + `CHECK (tickets >= 0)`, 단일 트랜잭션                    |
| 결제 → 티켓 발급   | **아니오**               | 결제 웹훅에서만. 클라이언트 호출로 발급 금지                             |
| 사적 채팅 오픈     | **아니오**               | 컬럼을 만들지 말고 messages RLS의 **파생 조건**으로. 시각 비교는 `now()` |
| 소개 대상 선정     | **아니오**               | 서버에서 호감 풀 ∩ 미소개로 계산                                         |
| pass / 재큐잉 제외 | **아니오**               | append-only 이력 테이블. `DELETE` 정책 미정의                            |
| 직장 인증          | **아니오**               | 메일 토큰 검증. 도메인 차단 목록은 보조 수단                             |
| 프로필·관심사 편집 | 행 소유자만              | RLS `auth.uid() = user_id`                                               |

#### N2. 접근성

- 본문 텍스트 대비 **4.5:1** 이상. `--primary`를 `#c72b10`으로 교체하면 현재 실패 항목이 한 번에 해소된다
- **비활성 상태에 `opacity`를 쓰지 않는다.** 필은 `--surface-subtle`, 라벨은 `--ink-muted`(5.42:1)
- 터치 타깃 **44px** 이상. 현재 온보딩의 `이전`(36px)·`다음`(40px)이 미달
- 종결어미가 있는 문장은 **16px 이상**

#### N3. 개인정보 · 약관

- 실명·생년월일·직업·사진·회사 이메일을 수집한다. **개인정보 처리방침과 이용약관, 가입 시 동의 흐름이 필요하다.** 현재 관련 문자열이 코드 전체에 0건
- 결제·환불 정책 고지

#### N4. 되돌릴 수 없는 행동

- 파기(pass) 버튼 라벨이 **동작과 일치**해야 한다. 현재 `다음에`(=연기)라고 적혀 있고 실제로는 되돌릴 수 없다
- 확인 단계 필요 (`alert-dialog` 기설치)
- 결과를 고지한다

```
                 -- 불변식: female_user 는 affinities(like) 를 준 사람이어야 한다
intro_exclusions id, user_a, user_b, reason, created_at        -- append-only
tickets          id, user_id, kind(meeting), state, purchased_at, used_at,
                 payment_id, refunded_at
meetings         id, intro_id, scheduled_at, place_name, place_kind,
                 confirmed_at, completed_at, completed_by[]
messages         id, intro_id, channel(coord|private), sender, body, created_at
feedbacks        id, meeting_id, author, result, text, created_at
events           id, user_id, name, props(jsonb), created_at
```

- `place_kind`는 **제약이 아니라 관측용**이다. 값 집합을 강제하지 않고 자유 입력 + 분류를 허용한다
- `intro_exclusions`는 **append-only**. 제외 이력이 지워지면 재큐잉 규칙이 무너진다
- 티켓 차감·발급은 **Postgres 함수 하나**로 감싼다. 클라이언트에서 `UPDATE tickets` 금지

## 완료 기준 (Acceptance Criteria)

**게이트 (베타 차단)**

- [ ] `chatOpen`이 false인 상태에서 `/chat/:id` 직접 접근 시 **서버가 거부**한다
- [ ] 남성 계정으로 여성 전용 선호 응답 화면에 접근·제출할 수 **없다**
- [ ] 클라이언트를 조작해 티켓 수량을 늘릴 수 **없다** (RLS 부정 테스트 통과)
- [ ] 티켓 0장에서 사용 요청이 **실패**한다 (현재는 통과한다)
- [ ] pass 버튼 라벨이 동작과 일치하고, 확인 단계와 결과 고지가 있다
- [ ] 개인정보 처리방침·이용약관 페이지와 가입 동의 흐름이 존재한다
- [ ] 티켓 화면에 **30,000원**과 환불 규칙이 명시된다

**기능**

- [ ] 온보딩 중간 이탈 후 재진입 시 이전 단계 입력이 유지된다
- [ ] 남성에게 공개되는 소개는 항상 그에게 호감을 준 여성이며, 동시 1명이다
- [ ] pass한 상대가 다시 큐에 등장하지 않으며, **누르기 전에 영구성이 고지된다**
- [ ] 티켓 사용 후 24시간 상대 무응답 시 **스케줄 잡이 자동 환불**한다
- [ ] 사적 채팅이 만남 전날 18시에 열리고, 확정이 그 시각 이후면 즉시 열린다
- [ ] 노쇼 신고가 상대 확인 절차를 거친 뒤에만 제명으로 이어진다
- [ ] 만남 확정 시 `place_kind`가 기록된다
- [ ] "만났어요" 확인이 저장되고 주간 만남 완료 수를 쿼리 하나로 뽑을 수 있다
- [ ] 피드백 제출이 실제로 저장된다
- [ ] 8개 이벤트가 발화한다

**품질**

- [ ] 본문 텍스트·버튼 라벨 대비 4.5:1 이상 (`--primary: #c72b10`)
- [ ] 비활성 버튼이 활성으로 오인되지 않는다 (`opacity` 미사용)
- [ ] 터치 타깃 44px 이상
- [ ] 화면 문구가 **예약 대행**을 약속하지 않는다
- [ ] "AI 인터뷰"·"만남 보장" 문구가 없다
- [ ] 404·에러 화면이 한국어다

## 구현 분담 (설계 · 코드 생성)

**원칙: 저렴한 모델에게 넘기는 것은 "구현"이 아니라 "테스트를 통과시키는 일"이어야 한다.**

| 레이어                     | 담당                                    | 산출물                                    |
| -------------------------- | --------------------------------------- | ----------------------------------------- |
| 스키마 · RLS 정책 · 불변식 | 설계 확정 (상위 모델)                   | 위 계약 + 정책 표 + **부정 테스트 3~5개** |
| 티켓 차감 · 게이트 · 배제  | 명세 + 테스트 선행 → 구현은 저렴한 모델 | 테스트가 스펙                             |
| 화면 · 폼 · 카피 · 상태 UI | Lovable / 저렴한 모델                   | 되돌릴 수 있는 영역                       |

필수 부정 테스트: ① 비소유자가 티켓 차감 시도 ② 게이트 시각 전 메시지 삽입 ③ 타인의 선호 응답 제출 ④ 제외된 쌍의 재큐잉 ⑤ 티켓 0장에서 사용.

테스트 없이 "RLS 짜줘"로 넘기면 **그럴듯한 정책이 나오고 뚫린다.** 실제로 클라이언트 게이트는 6곳 중 5곳이 맞고 1곳이 빠져서 뚫렸다.

## 확정된 정책 (2026-07-31 인터뷰)

| 항목              | 확정                                                                                                                                                                                                                                                                                                                               |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P1. pass한 쌍** | **영구 배제.** `intro_exclusions` append-only 테이블, `DELETE` 정책 미정의. 쌍 단위로 기록하며 전역 플래그를 쓰지 않는다. **사용자에게 결정 시점에 명시 고지한다** — 고지 없는 영구 배제는 동의 결함이다                                                                                                                           |
| **P2. 채팅 오픈** | 조율 채널은 **확정 즉시**. 사적 채널은 **만남 전날 18시(Asia/Seoul)**. 확정 시점이 이미 전날 18시를 지났으면 **즉시 오픈**한다 (당일·익일 확정 케이스)                                                                                                                                                                             |
| **P3. 환불**      | **24시간 무응답 시 자동 환불.** 기준 시각은 티켓 사용 시점. 확정 후 상대 사유 취소도 환불. 환불은 스케줄 잡이 자동 실행하며 사용자 요청을 기다리지 않는다                                                                                                                                                                          |
| **P4. 노쇼**      | 피해자에게 **티켓 1장 재발급** + 노쇼자 **영구제명**.<br>**판정 절차:** 신고 접수 → 상대에게 확인 요청 → 무응답 또는 노쇼 확정 시 제명. **단일 미검증 신고로 즉시 제명하지 않는다** — "만났어요" 1탭이 유일한 신호이므로 탭 누락으로 무고한 제명이 발생할 수 있고, 권역 밀도가 최대 리스크인 상황에서 공급을 스스로 깎는 일이 된다 |

### P3·P4가 요구하는 인프라

- **스케줄 잡**이 필요하다 (24h 무응답 판정, 전날 18시 채팅 오픈, 노쇼 확인 기한).
  → Cloudflare Cron Trigger. 이 요구가 Cloudflare 채택 근거를 하나 더 만든다
- **제명은 계정 상태 전이**다. 제명 시 진행 중 소개·티켓·환불 처리와 개인정보 삭제 정책이 함께 정의돼야 한다
