# 애프터 1인 운영 콘솔 상세 설계

2026-10-16 · 설계안 · 상위 문서: [제품과 운영 통합 설계](./product-operations-design.md)

목표는 운영자가 많은 숫자를 감시하는 것이 아니라 **지금 필요한 판단만 하고, 나머지가 처리됐는지 확인할 수 있게 하는 것**이다. 통계가 0인 것과 조회에 실패한 것을 절대 같은 상태로 표현하지 않는다.

## 1. 메뉴와 경로

기존 경로는 유지하며 묶음과 화면 역할을 바꾼다. 어드민은 계속 웹 전용이며 `admin.` 라우트의 네이티브 번들 제외 규칙을 유지한다.

```text
오늘
  운영 홈                 /admin
  작업함                  /admin/tasks                 신규
매칭 운영
  큐레이션                /admin/curation
  약속                    /admin/meetings
  장소                    /admin/places
회원과 안전
  회원                    /admin/members
  사진 검수               /admin/photos
  신고                    /admin/reports
  고객 문의               /admin/support
거래와 개선
  주문·티켓               /admin/orders
  수급·성과               /admin/insights              신규
자동화와 관리
  자동화·시스템           /admin/system
  운영 설정               /admin/settings              신규
```

회원 검색은 고정 상단. 검색 결과의 기본 표시는 이름·짧은 회원 ID·권역·상태이며 연락처는 마스킹한다. 이메일 검색어를 URL·외부 분석 로그에 남기지 않는다. 기존 `q` 파라미터는 이름 검색 호환만 유지하고 민감 검색은 요청 본문으로 전환한다.

사이드바에는 미처리 업무 뱃지를 최대 3종만 표시한다: 안전/거래 위험, 오늘 기한, 승인 필요. 모든 메뉴에 빨간 숫자를 붙이지 않는다. 모바일에서는 오늘·회원·더보기로 접근하며 긴 데이터 표를 억지로 축소하지 않는다.

## 2. 운영 홈

### 2.1 첫 화면 와이어프레임

아래 숫자는 구조 설명용 예시이며 운영 데이터가 아니다.

```text
┌ 애프터 운영   [회원 검색________________]    베타 · 강남   10:05 갱신 ┐
│ 운영 상태: 확인 필요 — 웹 알림 미지원 / 배포 버전 불일치             │
│ [긴급 1]       [오늘 기한 6]       [승인 대기 3]       [자동 처리 18] │
│                                                                    │
│ 지금 처리할 일                  [전체 작업함] [분류] [권역]          │
│ 우선순위  대상     필요한 일             남은 시간       상태        │
│ 긴급      회원 A   안전 신고 확인         2시간 초과       새 작업     │
│ 오늘      주문 B   취소 결과 대사         35분             확인 필요   │
│ 오늘      회원 C   사진 검수              3시간            새 작업     │
│                                                                    │
│ 선택한 작업 상세 → 근거 / 최근 이력 / 가능한 조치 / 처리 영향        │
│                                                                    │
│ 오늘 약속 4건   미확정 2건       공급 부족: 강남 · 후보 대기 8명      │
│ 자동화: 5개 정상 · 1개 지연      [실행 결과 확인]                     │
└────────────────────────────────────────────────────────────────────┘
```

상단 숫자는 서로 더하면 전체가 되는 분류가 아니다. 중첩 가능함을 명시하고 각각 필터 링크를 제공한다. 총 미처리 건수는 중복 없는 별도 count다. “자동 처리”는 업무 완료 건수, “알림 전달”은 채널별 결과로 분리한다.

### 2.2 상태와 데이터 계약

- 최초 진입: 작업함 skeleton을 표시하고 지표는 독립적으로 불러온다.
- 일부 실패: 정상 영역은 사용 가능. 실패 영역에 재시도와 마지막 성공 시각 표시.
- 전체 실패: “운영 현황을 확인할 수 없습니다.” 업무 없음/정상 배지 표시 금지.
- stale: 마지막 성공이 2분 이상 전이면 경과 표시, 5분 이상이면 “최신 상태 확인 필요”(초기 제안값).
- 자동 갱신: 전경에서 60초 간격, 브라우저 복귀 시 갱신. 작업 입력 중에는 순서를 바꾸지 않고 새 결과 배너만 표시.
- 조치 완료: 서버 결과를 받은 뒤 해당 행과 요약 재조회. UI에서만 숫자를 감소시키지 않는다.
- 필터: 권역, 업무 유형, 심각도, 기한, 상태. 정렬은 위험 등급→기한→발생시각→ID로 고정한다.
- 세부 운영 지표는 `/admin/insights`로 이동. 홈은 일·장애·오늘 약속 중심이다.

## 3. 건별 작업함

### 3.1 작업 카드가 답할 질문

1. 어떤 회원/주문/약속에 무슨 일이 생겼나?
2. 왜 지금 내 일이 되었으며, 언제까지 확인해야 하나?
3. 시스템이 이미 무엇을 해봤고 어떤 결과였나?
4. 지금 실행 가능한 조치는 무엇이고 상대·티켓에 어떤 영향을 주나?
5. 처리 결과를 무엇으로 확인할 수 있나?

작업 상세는 요약, 근거 타임라인, 조치 패널 순서다. 원본 화면으로 이동하더라도 선택 필터·스크롤·작업 ID를 보존한다. 위험하지 않은 읽기·메모만 키보드 빠른 실행을 허용하고, 금전·제재·대량 발송은 항상 확인한다.

### 3.2 작업 상태

```text
open → in_progress → resolved
  └→ waiting (기한·대기 주체 필수) → open
  └→ snoozed (다음 확인시각·사유 필수) → open
원본 문제 소멸 → resolved 또는 superseded
같은 문제가 해결 후 재발 → 새 발생 회차의 open
```

- `resolved`는 도메인 조건으로 확인한다. 신고가 pending인데 “완료”만 눌러 숨길 수 없다.
- 새 기록과 기존 기록은 동일한 문제 키 아래 회차로 연결한다. 갱신마다 새 작업을 쌓지 않는다.
- 안전/결제 결과 미상은 영구 보관함으로 치우기 금지. 보류는 이유와 다음 시각을 요구한다.
- 사용자 응답을 기다리는 것과 운영자가 처리하지 않은 것을 분리한다. waiting이어도 기한은 계속 관측한다.
- 수기 메모는 최소 정보로 작성하고 연락처·인증 원문 입력을 안내로 제한한다.

### 3.3 작업 유형과 내부 기준

아래 SLA는 새 대외 약속이 아니라 초기 내부 기준안이다. 기존 서버 만료 정책(24시간 응답 등)을 바꾸지 않는다. 안전 1차 확인 24시간은 기존 운영 기준을 이어받는다. 운영 시간은 기본 제안 `평일 10:00~19:00 KST`, 실제 설정 전 대외 노출하지 않는다.

| 작업           | 발생 조건                               | 우선순위 / 기한                                     | 기본 행동                     | 해결 조건                                             |

## 4. 기존 업무 화면의 구체적 개편

### 회원 상세

상단: 회원 상태, 소개 자격의 부족 조건, 진행 중 약속, 미처리 작업 수. 성인 확인·회사 메일·사진 검수는 별도 표시한다.

본문 탭: **요약 / 소개·약속 / 티켓·주문 / 문의·안전 / 운영 이력**. 프로필은 사용자와 같은 컴포넌트로 미리 본다. 다른 탭의 데이터를 읽기 위해 반복 검색하지 않는다. 개인 메모는 공개 소개 사유와 명확히 분리한다.

타임라인에는 사건·행위자·시각·이유·관련 객체·결과를 표시한다. “반환됨”을 누르면 원 티켓과 대체 티켓, “취소 확인 중”을 누르면 주문 대사로 이동한다. 관리자 계정·테스트 계정은 모집단에서 기본 제외한다.

### 큐레이션

- 왼쪽: 지금 소개 가능한 수신자, 대기시간과 막힌 이유. 공급이 없는 회원은 별도 탭.
- 가운데: 후보 2~4명 비교. 같은 권역, 자격, 기존 호감·제외 이력, 원문 소개를 우선 표시.
- 오른쪽: 규칙 기반 순서 초안과 선택적 AI 브리프. AI 실행은 개별 요청 시만, 전체 풀 일괄 생성 금지.
- 저장 전: 전송될 대상·미공개 대기 대상·공개 사유·영향을 미리 보기. 저장 순간 자격과 호감 재검증.
- 프로필/자격이 바뀌면 기존 초안을 경고하고 충돌 응답으로 새로고침. 운영 메모가 공개 reason에 섞이지 않게 입력칸 분리.
- 초안 자동 채우기는 기존의 단순 후보 순서를 개선하는 것으로 시작한다. 모델 점수로 순위를 정하지 않는다.

### 약속

오늘/이번 주, 응답 대기, 재조율, 결과 대기, 취소로 나눈다. 요청 기한, 날짜 후보의 유효성, 장소 상태, 알림 전달 여부를 같은 행에서 볼 수 있다. 캘린더는 날짜를 탐색하는 보조 뷰이고 기한 초과 목록이 기본이다.

일정 변경·강제 취소는 양측 영향과 티켓 반환 여부를 확인한다. 운영자가 대신 수락하는 기능은 추가하지 않는다. 동일 사용자의 확정 일정 충돌은 요청 수락 트랜잭션에서 막고 새 날짜 선택을 안내한다.

### 주문·티켓

베타 신청/실결제/샌드박스를 명확히 구분한다. 전역 결제 플래그가 아니라 주문 생성 시 기록된 모드를 기준으로 처리한다. 입금/승인 상태, 발급 수량, 사용·만료·반환 계보, 취소 예약과 PG 상태를 함께 본다.

“반환 티켓”과 “카드 결제 취소”는 서로 다른 라벨/행동이다. 결과 미상에서는 새 결제를 권하거나 티켓 잠금을 임의 해제하지 않는다. 대사는 먼저 읽기 전용 조회, 검증된 결과에 따라 안전하게 완료한다. 임의 보상·환불은 확인과 사유 필수다.

### 문의·신고

문의는 대화형 이력으로 확장하고, 미답변/회원 답변 대기/답변됨/종료를 구분한다. 승인 FAQ 템플릿은 수정 가능하고 전송 전 미리보기한다. 신고는 별도 판정 흐름을 유지하되 같은 회원·약속 링크로 연결한다. 반려·제재 사유와 이의 제기까지 추적한다.

사진은 검수 중인 버전을 고정해서 보여준다. 운영자가 보는 동안 회원이 바꾼 사진에 이전 승인 결과가 적용되지 않게 버전 충돌을 처리한다.

## 5. 자동화 설계

### 5.1 모드와 안전 장치

모든 새 규칙의 상태는 `off / observe / approval / auto` 중 하나다. 관찰 모드는 조건을 계산하고 “실행했다면 대상 N건”만 남긴다. 승인 모드는 대상·본문·영향의 미리보기와 만료시각을 저장한다. 승인 후에도 실행 직전에 조건과 버전을 다시 확인한다.

공통 제어: 규칙 버전, 최소 실행 간격, 사용자별 빈도 제한, 하루 최대 건수/비용, 재시도 상한, 유효시간, 전체/개별 중지, 실행 이력. 외부 발송 승인은 대상과 본문 hash를 고정하며 바뀌면 재승인한다.

| 규칙                    | 초기 모드                | 자동화할 것                         | 사람이 판단할 것           |
| ----------------------- | ------------------------ | ----------------------------------- | -------------------------- |
| 작업 생성·우선순위 갱신 | observe → auto           | 정해진 조건의 누락 탐지·중복 합치기 | 임계값 변경                |
| 기존 만료·반환          | 현행 유지                | 기존 서버 규칙의 기한·멱등 처리     | 새로운 반환 사유/정책      |
| 후보 초안               | approval                 | 자격 필터·순서 초안·중복 제거       | 누구를 실제로 소개할지     |
| 인증/사진 지연 안내     | approval                 | 대상/문구 제안                      | 채널 동의 및 승인          |
| 약속 리마인드           | approval → 제한적 auto   | 아직 유효한 요청에 정해진 안내      | 예외 조율                  |
| 알림 일시 실패          | 검증 후 auto             | backoff 재시도                      | 영구 실패·채널 없음        |
| 결제 대사               | observe → 읽기 조회 auto | 외부 결과 확인·불일치 탐지          | 신규 취소·재결제·임의 보상 |
| AI 편집/브리프          | 사용자/운영자 요청       | 초안과 근거 생성                    | 채택/공개                  |
| 운영 요약               | approval → auto          | 서버 집계 기반 일일 요약            | 모집·예산 변경             |
| 제재·노쇼 판정          | 자동 실행 금지           | 자료 모으기·기한 알림               | 판정·해제                  |

기존 규칙을 새 워커로 옮길 때는 동일 작업이 두 곳에서 실행되지 않게 단일 소유자를 지정한다. 자동화 전역 중지는 새 발송/AI/소개 초안을 멈추되 기존 티켓 무결성과 필요한 만료 처리는 유지한다. 전체 시스템 비상 중단은 별도 운영 절차다.

### 5.2 알림의 의미

다음 상태를 혼동하지 않는다.

```text
업무 사건 발생 → 인앱 알림 등록 → 채널 발송 대기
  → 공급자 접수 / 재시도 / 최종 실패 / 채널 없음 / 기한 경과로 생략
인앱 조회·읽음은 별도 사건
```

APNs의 성공 응답은 실제 사용자 열람 증명이 아니다. 메일도 접수·반송·읽음 추정은 별개다. 외부 도달률과 인앱 읽음률을 같은 분모로 합치지 않는다.

- 중요 약속 알림은 현재 상태·기한을 다시 확인한 뒤 전송한다. 취소된 약속/탈퇴/차단/철회 후 과거 알림 재발송 금지.
- 웹용 외부 채널이 없는 회원은 “채널 없음”으로 명시한다. 필요 시 운영 작업을 만든다.
- 개인 이메일 재도입안은 대표 승인 후 검증 주소·서비스 알림 설정·실수신 테스트를 갖춰 켠다. 회사 메일로 조용히 대체하지 않는다.
- 서비스 알림과 마케팅 동의를 분리한다. 야간 리마인드 유예는 새 제안 규칙에 적용하며, 원 응답 기한을 임의로 연장하지 않는다.
- 운영자 외부 경보는 사건 키당 최초 1회 + 미해결 재알림 + 복구 1회. 단순 성공 로그는 일일 요약으로 묶는다. 외부 본문은 건수·유형·인증이 필요한 링크만.
- 동일 발송의 중복 가능성은 아웃박스와 lease로 줄인다. 공급자 응답 직후 장애 같은 경우까지 무조건 exactly-once라고 주장하지 않는다.

### 5.3 시스템 상태

`정상 / 지연 / 실패 / 미실행 / 관측 불가 / 비활성(의도됨)`을 구분한다. 정상 조건은 설정 활성뿐 아니라 최근 성공 완료와 결과 관측이다.

5분 주기 작업은 최근 성공이 15분 이상 없으면 지연, 30분이면 높음 경보를 초기 기본으로 제안한다. 각 작업의 주기·허용 시간으로 계산하며 시간별 작업에 그대로 적용하지 않는다. cron이 HTTP를 보냈다는 성공과 Edge Function의 실제 처리를 분리한다.

CI·배포는 예상 커밋, 실제 웹 커밋, 마지막 성공, 실패 단계와 링크만 표시한다. 토큰/시크릿 값은 수집하지 않는다. 외부 상태 확인에 실패하면 “관측 불가”, 배포 완료로 추정하지 않는다. P0에서는 수동 증빙 링크로 시작하고 자동 연동은 P1이다.

## 6. 수급·성과 대시보드

기본 필터는 가입 기수, 권역, 성별 흐름, 관측 기간(7/14/28일), 베타/유료/테스트 제외다. 모든 비율은 분자/분모, 기준 시각, 표본 수를 함께 보여준다. null·표본 없음·0을 구분한다.

| 지표               | 정의                                                                        | 운영 행동                                        |
| ------------------ | --------------------------------------------------------------------------- | ------------------------------------------------ |
| 소개 가능 회원     | 최신 자격 함수 통과 + 휴식/정지/탈퇴 제외                                   | 부족 권역과 막힌 자격 원인 파악                  |
| 즉시 큐레이션 가능 | 유효 호감·동일 권역·제외 이력 없음·양측 자격 충족                           | 운영자가 지금 처리할 후보량                      |
| 첫 소개 7일 도달률 | 관측 7일이 지난 자격 충족 기수 중 7일 내 첫 소개 경험 인원 / 해당 기수 인원 | 가입 확대보다 공급/처리 병목 개선                |
| 진행 중 대기       | 단계 진입 후 미완료 회원 수와 대기 나이 p50/p90                             | 아직 기다리는 사람을 숨기지 않음                 |
| 완료 소요시간      | 해당 단계 완료자의 진입→완료 시간, 완료 표본 명시                           | 처리 속도 관측. 전체 예상 대기시간으로 오인 금지 |
| 소개 열람률        | 같은 전송 기수의 관측 기간 내 열린 카드 / 전달 카드                         | 티저·후보 적합성·알림 점검                       |
| 약속 확정률        | 같은 요청 기수의 기한 내 확정 요청 / 요청                                   | 날짜/장소·무응답 병목 점검                       |
| 실제 만남          | 양측 확인 / 한쪽 확인 / 미확인 / 분쟁을 분리                                | 확정 수를 실제 만남으로 부르지 않음              |
| 안전               | 신고 건수, 관련 만남 분모, 기한 초과, 반복 사유                             | 판단 품질과 대응 부하 확인                       |
| 운영 시간          | 작업 시작~종료에서 장시간 비활성 제외, 수동 정정 가능                       | 건당 원가·하루 용량 계획                         |
| 자동화 효용        | 시도/성공/생략/실패/수기 재처리                                             | 자동 실행률보다 재처리 감소 확인                 |
| AI 효용            | 채택/수정/폐기, 근거 오류, 지연, 토큰·비용                                  | 모델 비용보다 검토 시간·품질 비교                |
| 모집 효율          | 캠페인별 자격 충족자 비용, 소개·만남 전환                                   | 실사용 가능 수급에 광고 집중                     |

완료한 사람만으로 전체 대기시간을 예측하지 않는다. 중도 이탈과 휴식을 표시하고, 데이터가 충분해지면 검열 자료를 다루는 생존분석을 P2로 검토한다. 초기에는 “현재 대기 N명, 최장 N일, 완료 표본 N명”으로 충분하다.

## 7. 설정

허용 항목: 권역별 내부 SLA, 운영 가능 시간, 알림 빈도·일일 상한, 승인된 템플릿, 규칙 모드, 관찰 기간, 모집 기수·정원(승인값). 모든 설정 변경에는 변경 전후·행위자·사유·버전을 남긴다.

제한 항목: 본인인증 필수 플래그, 실결제 활성화, 개인정보 정책 발효, 관리자 권한. 일반 토글로 두지 않고 사전 체크리스트·강화 인증·영향 미리보기를 요구한다. 비밀키는 이 화면에서 입력/조회하지 않는다.

## 8. 1인 운영 루틴과 휴무

1. 오전: 위험/관측 불가/기한 초과부터 확인, 사진과 문의 처리.
2. 큐레이션 시간: 준비된 후보 초안만 검토·저장. 공급 부족은 모집 큐로 분리.
3. 저녁 전: 오늘·다음 날 약속, 응답 대기, 전달 실패 확인.
4. 종료: 미해결 건마다 다음 확인시각을 남기고 자동화 결과와 예산 확인.

‘일 30분이면 충분’ 같은 보장은 하지 않는다. 실제 처리 시간을 2주 기록해 SLA·모집량을 조정한다. 휴무/부재 모드는 신규 모집과 신규 소개 전송의 승인 일정을 조정하되 진행 중 약속·취소·신고 창구를 없애지 않는다. 대체 대응자가 없으면 그 사실에 맞는 운영시간을 안내한다.

## 9. 운영 완료 기준

- 사진 검수·수기 소개·문의 답변·신고 판정·베타 지급·알림 복구를 SQL 없이 수행.
- 홈의 숫자를 누르면 같은 조건의 실제 목록이 열리고 합계가 페이지 크기에 잘리지 않음.
- 중복 탭/네트워크 재시도/두 창 동시 작업으로 두 번 지급·발송·판정하지 않음.
- 잠시 보류한 작업이 정해진 시각에 다시 나타나며, 해결되지 않은 건을 정상으로 숨기지 않음.
- 모든 민감 조치가 회원·주문·약속의 타임라인에서 추적됨.
- 시스템 장애 중에도 읽기 가능한 기존 정보와 오류 상태를 구별하고 안전한 문의 경로 유지.
- 제한된 역할의 회원은 운영 API·목록·원문 메모에 접근할 수 없음.
