# 새 커플로 매니저 전체 흐름 테스트

여성의 첫 호감 전부터 시작하도록 준비한 로컬 전용 환경이다. 아래 0건 표기는 최초 준비 당시 상태이며 사용자가 진행한 기록은 초기화하지 않는다. 기존 `5190` 계정과 약속은 유지한다. 운영의 상담·기억 저장·일정 실행은 OFF를 유지한다. 2026-10-28 화면의 명칭은 **매니저**로 통일했다. [최신 변경과 실제 AI 검증 한계](qa/personal-manager-reading-2026-10-28.md)를 확인한다.

## 접속과 계정

앱은 <http://127.0.0.1:5191/login>이다. 남성은 일반 창, 여성은 시크릿 창이나 다른 브라우저, 운영자는 별도 브라우저 프로필을 사용한다. 같은 브라우저의 일반 탭끼리는 로그인 계정이 공유된다.

| 역할   | 이메일                             | 이름               |
| ------ | ---------------------------------- | ------------------ |
| 남성   | `cycle-manual-male@verify.local`   | 테스트 지훈        |
| 여성   | `cycle-manual-female@verify.local` | 테스트 지안        |
| 운영자 | `cycle-manual-admin@verify.local`  | 수동 테스트 운영자 |

공통 비밀번호는 `AfterLocal!2026`이다. 공개 가능한 로컬 합성 계정용이며 운영에서 재사용하지 않는다. 프로필 사진은 실제 사람이 아닌 테스트 표식 이미지다. 가입·인증·프로필 완성은 미리 준비했고, 호감·소개 큐·소개 열람·티켓·주문·약속은 0건부터 시작한다. 실제 가입 인증 성공을 검증하는 계정은 아니다.

## 따라 할 순서

1. **남성 프로필 수정**: 홈에서 비서에게 `퇴근 후 일상 답변을 더 자연스럽게 다듬어줘` → **비서와 프로필 다듬기**. 요청과 AI 처리 동의를 확인해 초안을 만든 뒤, 현재/수정안을 비교하고 **이대로 프로필에 반영**해야 공개된다. **프로필 수정하기**의 기존 수동 편집도 유지된다. 새 기능이 OFF이면 수동 편집으로 안내한다. [실제 LLM 검증과 한계](concierge-llm-local-qa.md)를 먼저 확인한다.
2. **여성 호감**: 여성 홈에서 `호감 보내줘` → **소개 확인하기** → 테스트 지훈인지 확인 → **좋아요**. 이때는 만남 확정도, 남성에게 공개된 소개도 아니다.
3. **운영자의 소개 승인**: 운영자 로그인 → `/admin/curation` → 작업 대상에서 **테스트 지훈** 선택 → 테스트 지안 **큐에 추가** → 큐레이션 사유 입력 → **큐 저장**. 이 단계는 현재 수동이다. 비서가 자동으로 운영자 심사를 대신하지 않는다.
4. **남성 소개 티켓 구매**: 남성 홈에서 `티켓 구매하고 싶어` → **티켓·가격 확인**. **소개 티켓 1장**을 골라 결제하기 → 결제 화면의 **로컬 모의 카드** 안내 확인 → 결제하기 → **청구 없이 모의 결제 승인**. 실제 카드 입력·청구는 없다. 취소를 먼저 눌렀다면 **결제 이어하기**로 같은 주문을 재개한다.
5. **남성 소개 열람**: 홈에서 `이 여자 소개시켜줘` → **소개 확인하기** → **소개 티켓 1장 쓰고 열기**. 테스트 지안의 프로필인지 확인한다. 여러 명을 한꺼번에 공개하는 방식이 아니라 운영자가 정한 순서대로 한 사람씩 연다. 소개 설명이 로컬에서 켜져 있으면 처리 안내를 확인하고 **매니저와 함께 읽기**를 누른다. 현재 실제 소개 LLM 품질은 미완료이며 검증 실패 시 AI 설명이 아닌 공개 프로필 기반 내용으로 전환한다. 권한이나 티켓 단계를 우회하지 않는다.
6. **만남 티켓 구매와 요청**: 상점에서 **만남 티켓 1장**도 같은 모의 방식으로 구매한다. 홈의 **일정 정리** 빠른 메뉴 → **만남 요청 확인** → 평일 저녁 후보 날짜·시간과 가상 장소 입력 → **후보 1개로 요청하기**. 여기서 만남 티켓이 사용되고 여성의 답변을 기다린다. 상담에 `약속 잡아줘`를 보내면 기록에는 안전한 약속 목록 링크가 남는다. 실제 현재 단계에 맞는 실행 화면은 빠른 메뉴에서 연다.
7. **여성 비서로 약속 확정**: 여성 홈의 **일정 정리** 빠른 메뉴 → **비서와 일정 정리** → 제안받은 시간 선택 → **전달 전 초안 보기**. 초안만으로 약속이 확정되면 안 된다. 날짜·장소·참석 안내 확인 후 체크 → **승인하고 확정하기**.
8. **양쪽 확인**: 두 계정 홈의 **약속 보기**에서 일시·장소가 같아야 한다. 상세 안의 직접 대화도 유지된다. 운영자 `/admin/meetings`에서 같은 약속의 상태를 확인한다.

## 2026-10-28 화면 확인용 커플

처음부터 진행할 위 `5191` 계정은 호감·주문·약속 0건을 유지했다. 별도 `5192`에서는 실제 로컬 DB로 아래 흐름을 완료해 약속과 채팅을 바로 볼 수 있다.

| 역할 | 이메일                               |
| ---- | ------------------------------------ |
| 남성 | `cycle-tour1028-male@verify.local`   |
| 여성 | `cycle-tour1028-female@verify.local` |

공통 비밀번호는 동일한 `AfterLocal!2026`이다. <http://127.0.0.1:5192/login>에서 각각 다른 브라우저로 로그인한다. 홈의 **약속 보기**에서 상대 채팅, 채팅 입력창 위 **내 비서에게 물어보기**에서 개인 상담을 연다. 홈에는 최근 대화 3개, **대화 전체 보기**에는 같은 계정의 전체 기록이 나온다. 새로고침해도 이어지며 다른 계정의 상담은 보이지 않는다.

이번 시연은 여성 호감·운영 큐 승인·남성 소개/만남 티켓 모의 결제·날짜/장소 제안·여성 초안 승인·쌍방 메시지 전송을 완료했다. 상태/일정/결제 안내는 규칙 응답으로 검증했으며, 해당 두 계정의 LLM 실행 기록은 0건이다. 실제 모델 품질을 이번 검증의 성과로 주장하지 않는다. 자유 상담이나 프로필 생성 버튼을 직접 누르면 로컬에 설정한 API 키로 호출될 수 있다.

현재 비서는 자유 입력을 필요한 작업 화면으로 연결한다. 대상 확인·호감·티켓 사용·모의 결제·일정 확정은 사용자가 구조화된 화면에서 승인한다. 채팅 한마디로 상대에게 메시지를 전송하거나 장소를 예약하지 않는다. 이 서비스 명령들은 LLM을 호출하지 않는다.

## 이어지는 상담과 기록 관리

홈에서 `첫 만남이 긴장돼요`처럼 자유 질문을 쓰면 비공개 상담으로 이어진다. 새 개인화·보관 안내에 한 번 동의한 뒤 직접 전송해야 AI가 호출된다. **이 내용 기억하기**는 없어졌으며 대화는 초기화·철회·탈퇴 전까지 이어진다. 기존 저장 선호는 **대화 설정**에서 수정·삭제할 수 있다. 로컬 Edge의 Anthropic 키를 사용하므로 자유 상담·맞춤 팁·매니저 소개·프로필 수정의 명시적 생성은 모델 비용이 발생한다. 화면 이동·상태 안내·일정 승인·모의 결제에는 LLM을 쓰지 않는다.

동의·기억 수정/삭제·철회 등 상세 확인은 [기존 비서 테스트 안내](assistant-local-test.md)의 A·C·E를 새 계정으로 진행한다. 기존 계정을 초기화할 필요는 없다.

## 참석 확인과 후기까지 시간을 이동할 때

약속 확정 후 다음 명령은 **새 커플의 현재 약속만** 옮긴다. 전체 회원 알림이나 자동취소 배치를 실행하지 않는다.

```bash
# 현재 상태 확인. 기록 변경 없음.
npm run assistant:cycle -- status

# 약속을 20시간 뒤로 이동 → 양쪽에서 참석 확인
npm run assistant:cycle -- checkin

# 약속을 2시간 전으로 이동 → /feedback?meetingId=출력된_ID
npm run assistant:cycle -- feedback
```

두 계정에서 같은 `meetingId`로 후기를 작성한다. 시간 이동은 자정 자동 알림이나 실제 외부 메시지 발송 검증을 대신하지 않는다.

## 서버 다시 켜기

기존 로컬 Supabase와 Edge가 실행 중인 상태에서:

```bash
cd /Users/ys.choi/dev-private/after
npm run assistant:cycle -- prepare
npm run assistant:cycle:dev
```

`prepare`는 이미 만든 새 계정·기억·진행을 초기화하지 않는다. 전역 로컬 설정이나 기존 `5190` 서버를 바꾸지 않는다. 새 계정을 만들 때는 기존 로컬 결제·상담·기억·일정 설정이 ON이어야 하며, 도구가 그 설정을 대신 켜지 않는다. Supabase와 Edge를 다시 띄우는 순서는 [기존 안내의 서버 실행](assistant-local-test.md#4-서버를-다시-켜야-할-때)을 따른다. 기존 계정용 `reset` 명령은 사용하지 않는다.

첫 준비가 브라우저 미설치 등으로 중단된 경우에만 `npm run assistant:cycle -- recover-incomplete` 후 `prepare`를 다시 실행한다. 이 복구는 미완성·미사용 합성 자원만 삭제한다. 완료된 계정, 호감·주문·비서 기록 등이 생긴 계정이나 사람이 올린 사진은 복구 대상에서 제외하고 중단한다.

모의 결제는 `assistant:cycle:dev`가 실행한 **127.0.0.1:5191 개발 서버와 지정한 새 남성 계정에만** 허용한다. 실제 Toss SDK를 로컬 대역으로 바꾸며, 원래 주문과 원장 처리는 실제 로컬 DB 함수로 수행한다. 승인하지 않은 성공 URL, 다른 계정·금액·Origin은 거절한다. 서버 재시작 전에 승인만 하고 확인하지 못한 주문은 자동 승인되지 않으므로, 상태를 확인하고 모의 창에서 다시 승인한다. 운영 빌드에는 이 대역이 포함되지 않는다.

구매 후 **미사용 주문 취소**도 모의 원장으로만 처리한다. 이미 쓴 주문은 거절하며, 운영자의 PG 재정산 버튼은 차단해 외부 결제사로 전달하지 않는다.

## 이번 환경의 검증 범위

2026-10-25 Chromium·WebKit에서 아래 수동 전체 흐름을 통과했다. `npm run check`와 독립 코드 리뷰도 통과했다. 리뷰에서 구매 후 취소의 외부 PG 전달 가능성과 미완성 준비의 복구 누락을 찾아 수정하고 재검토했다. 새 커플은 호감 전 상태를 유지했다.

`npm run test:manual-cycle`은 사용자용 새 커플이 아닌 독립 `qa-manual` 커플로 실제 브라우저 흐름을 검증하고, 자신이 만든 QA 계정만 정리한다. 원래 계정 기록과 공통 설정의 해시가 전후 일치해야 통과한다. 사용자 테스트 중에는 같은 `5191` 포트를 쓰는 이 검사를 동시에 실행하지 않는다.

- 비서 진입 → 실제 프로필 수정·공개 → 여성 호감 → 운영 큐 승인 → 남성 모의 결제 → 소개 열람 → 만남 요청 → 여성 비서 초안·건별 승인 → 확정.
- 모의 결제 취소·동일 주문 재개·확인 재전송 시 티켓 중복 없음.
- 로그인 없는 요청, 여성의 결제 요청, 잘못된 금액·Origin, 승인 전 위조 성공 응답 거절.
- 모의 결제창 320/390/1440px·라이트/다크, 가로 넘침 및 심각·치명 접근성 위반 검사.
- 실제 PG 요청 없음. 실결제·통신사 인증·외부 발송·실기기 확인과 이번 실제 LLM 품질 평가는 포함하지 않는다.
