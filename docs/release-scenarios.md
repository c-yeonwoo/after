# 출시 전 검증 시나리오

작성 2026-08-12. **실사용자를 받기 전 마지막 관문.**

목적은 "기능이 도는가" 가 아니라 **"운영자 한 명이 이 서비스를 돌릴 수 있는가"** 다.
순수 큐레이션이라 운영자가 멈추면 서비스가 멈추고, 돈이 오가는 경로가 넷
(소개 티켓·만남 티켓·환불·보상 재발급)이라 잘못되면 사용자 지갑에서 실제로
빠진다. 그래서 정상 흐름보다 **돌발상황과 엣지케이스에 지면을 더 쓴다.**

---

## 0. 목 데이터 — 왜 이 구성인가

| 계정 | 성별 | 상태 | 이 계정으로 검증할 것 |
|---|---|---|---|
| 운영자 | — | `role=admin`, `paused_at` 있음 | 어드민 전체. 회원 지표에서 빠지는지 |
| 여성1 서연 | F | 사진 승인됨 | 정상 경로. 평가 → 호감 → 소개 → 만남 |
| 여성2 지우 | F | **사진 검수 대기** | 검수 전 후보 풀 제외(s18). 승인 후 복귀 |
| 여성3 하람 | F | 사진 없음 | 사진 없는 회원은 게이트를 통과해야 한다 |
| 남성1 연우 | M | 티켓 0장 | 티켓 없이 열람 시도 → 차단. 구매 흐름 |
| 남성2 민수 | M | 소개·만남 티켓 보유 | 정상 경로 끝까지(만남 확정) |
| 남성3 지호 | M | **소개 받기 OFF** | 큐레이션 대상에서 빠지는지 |

여성 3·남성 3 이 최소 구성인 이유: 큐를 **3장 이상** 세워 "상위 3장만 전송,
나머지 대기" 를 확인해야 하고, 남성 쪽도 세 상태(티켓 없음·정상·수신 거부)가
동시에 있어야 큐레이션 목록의 정렬과 배제를 한 화면에서 볼 수 있다.

**동시 세션.** dev 서버를 포트별로 띄운다. 포트가 다르면 origin 이 달라
localStorage 가 분리되므로 **운영자·남성·여성을 동시에 로그인** 해둘 수 있다.
같은 포트에서 탭만 나누면 세션이 서로를 덮어쓴다.

## 1. 어드민 세팅

앱에 운영자 승격 경로가 **없다.** 첫 운영자는 SQL 로 심는다.

```sql
update profiles set role = 'admin' where company_email = '...';
```

- [x] A1 운영자가 `/admin` 에 들어간다
- [x] A2 일반 회원이 `/admin` 에 들어가면 "운영자만 볼 수 있는 화면입니다"
- [x] A3 비로그인이 어드민 RPC 를 직접 부르면 401
- [x] A4 **운영자가 회원 수(규모 지표)에서 빠진다** — 배포마다 최소 1명이라 항상 틀린다
- [x] A5 운영자 계정은 정지 화면이 아예 안 뜬다(마지막 운영자를 정지시키면 아무도 못 들어온다)

## 2. 회원 온보딩

- [x] B1 회사 이메일로 OTP 로그인 (개인 메일 도메인은 거부)
- [x] B2 7단계 온보딩 완료 → `onboarding_step = 7`
- [x] B3 사진을 올리면 `photo_state = pending` **이 되고 후보 풀에서 빠진다**
- [x] B4 운영자가 승인하면 후보 풀로 돌아온다
- [x] B5 운영자가 반려하면 사유가 **사용자에게 보인다**
- [x] B6 반려 후 다시 올리면 `pending` 으로 복귀(트리거)
- [x] B7 **사진이 없는 회원은 게이트를 통과한다** — 사진은 온보딩 필수가 아니다

> **엣지 B3 의 대가**: 사진을 올리면 검수까지 아무에게도 안 보인다. 이미 승인된
> 사람이 사진을 **바꿔도** 마찬가지다. 대시보드 "사진 검수 대기" 가 곧 지금
> 보이지 않는 회원 수다 — 이 숫자가 쌓이면 매칭이 멈춘다.

## 5. 남성 소개 열람 — 돈이 처음 빠지는 곳

- [x] E1 큐에 카드가 있고 티켓 0장 → **차감 없이** "소개 티켓 사기"
- [x] E2 홈에 들어가기만 해도 **티켓이 빠지지 않는다**
- [x] E3 소개 탭에 들어가기만 해도 **티켓이 빠지지 않는다**
- [x] E4 상점에서 소개 티켓 주문(1장 5,000 / 5장 22,000)
- [x] E5 열람 버튼을 누르면 1장 차감 + 프로필 공개
- [x] E6 다시 눌러도 **추가 차감 없음**(불변식 2: 동시 1건)
- [x] E7 패스 → 티켓 **환불 없음**(소멸), 큐에서 제거, 영구 배제
- [x] E8 패스 후 큐의 4번째가 승격된다
- [x] E9 상점에서 만남 티켓 탭 → 다른 가격·다른 약관 문구

> **엣지 E2·E3 은 회귀 위험이 가장 큰 곳이다.** v1 에서 `open_intro()` 는 공짜라
> 홈과 소개 탭이 진입 시 자동 호출했다. 유료화 후에도 그대로 뒀다면 탭을 여는
> 것만으로 5,000원이 빠졌다. 화면을 고칠 때마다 이 두 항목을 다시 본다.

| s26 | 큐 만료 크론이 3장을 지우고 "1" 이라고 로그 | 남성 수를 셌다 | 지운 카드 수를 센다 |

### 앱(iOS)에서 확인한 것

- 시뮬레이터에서 **실제 로그인**(OTP 메일 → 코드 입력)까지 동작. 로컬 Supabase 에

> 검증하면 **운영 DB 를 만지게 된다.**

## 11. 출시 판정 — "SMTP 만 붙이면 되는가"

**아니다.** SMTP 는 가장 급한 하나일 뿐 유일한 것이 아니다.

시나리오 81개가 다 통과했으므로 **제품 로직은 실사용자를 받을 수 있는 상태**다.
남은 것은 전부 **설정과 외부 연동**이고, 그중 둘은 없으면 서비스가 성립하지 않는다.

| 항목 | 상태 | 없으면 벌어지는 일 | 막는가 |
|---|---|---|---|
| 커스텀 SMTP | ❌ | 기본 메일이 시간당 2통 — 세 번째 사용자부터 로그인 불가 | **막는다** |
| 결제 게이트웨이(토스) | ❌ | 주문만 쌓이고 티켓이 안 나간다. 유료화가 전제인 v2 에서는 서비스가 성립하지 않는다 | **막는다** |
| 알림 발송 설정 | ⚠️ | 소비자는 **이미 있다**(pg_cron → pg_net → `send-notifications`). `RESEND_API_KEY`·`APP_URL`·vault 시크릿(`edge_function_base_url`·`service_role_key`)이 없으면 아웃박스가 쌓이기만 한다 | 막지는 않음 (기능은 돌고 알림만 안 감) |
| 로그인 메일 템플릿 | ⚠️ | 지금 제목이 `Your Magic Link` — 한국어 서비스의 첫 메일이 영문 기본 문구다. `[auth.email.template.magic_link]` 미설정 | 막지는 않음 |
| 앱 호스팅 확정 | ⚠️ | `site_url`·리다이렉트·`APP_URL` 이 `127.0.0.1` 로 남아 있다. 메일 링크가 로컬을 가리킨다 | 알림·메일 링크를 막는다 |

### 순서

1. **SMTP + 로그인 메일 템플릿** — 이게 없으면 아무도 못 들어온다. 템플릿은 같은
   설정 파일에서 함께 처리하는 게 싸다.
2. **호스팅 주소 확정 → `site_url`·`APP_URL`·vault 시크릿** — 1번의 메일 링크가
   여기에 붙으므로 사실상 같은 작업이다.
3. **토스 결제 키** — 여기까지 해야 v2(유료 소개 티켓)가 의미를 갖는다.
4. (선택) `RESEND_API_KEY` — 2번에서 함께 넣으면 알림까지 살아난다.

### 첫 운영자 심기

앱에 승격 경로가 없다. 배포 후 SQL 한 줄이 필요하다.

```sql
update profiles set role = 'admin' where company_email = '...';
```

이건 의도된 것이다 — 화면에 승격 버튼이 있으면 그 버튼이 곧 권한 상승 경로가 된다.
