# 브랜드 2차 폴리시 — 실행 기록

> 1차(D8·D14)는 **무엇을 쓸지 결정**했다. 2차는 **그 결정이 실제 코드에 있는지 확인**하고,
> 결정과 코드가 갈라진 지점을 메웠다.
>
> 검증: `bun run check:contrast` (모든 역할별 대비 재계산) · `tsc --noEmit` · 실제 브라우저 워크스루

## 가장 큰 발견 — D14 가 코드에 없었다

README·PRD 에는 D14 가 확정으로 적혀 있었다:

> 브랜드 컬러 = 코럴 `--primary: oklch(0.54 0.195 32)` = `#c72b10`.
> 현행 `#f94a2d`는 대비 3.23/3.07로 AA 미달. 이 값은 5.19/4.93 통과.

그런데 `src/styles.css` 는 `--primary: var(--brand-600)` = `oklch(0.657 0.216 32)` 였다.
OKLab→sRGB 로 직접 변환해 보니 **`#f94a2d`** — 즉 PRD 가 "미달"이라고 지목한 바로 그 색이
그대로 쓰이고 있었다. 계산한 대비값도 PRD 가 적어둔 수치와 정확히 일치했다:

|                          | 텍스트/배경   | 필(흰 글씨)   |
| ------------------------ | ------------- | ------------- |
| 코드에 있던 값 `#f94a2d` | **3.07 FAIL** | **3.23 FAIL** |
| D14 확정값 `#c72b10`     | 4.93 PASS     | 5.19 PASS     |

수치가 PRD 와 소수점까지 맞았다는 게, 계산이 맞고 **코드가 결정 이전 상태에 머물러
있었다**는 이중 확인이 됐다.

**교훈:** 버그 4·7 과 같은 계열이다 — "결정했다"와 "코드에 있다"는 다르고, 색은 특히
사람 눈으로 "대충 코럴 맞네"로 통과되기 쉽다. 그래서 스크립트(`scripts/check-contrast.mjs`)로
고정했다.

## 고친 것

### 1. `--primary` / `--primary-strong` 재정의

`--primary` 를 D14 값으로 올리자 새 문제가 생겼다: 기존 `--primary-strong`(`brand-700`,
`#d03420`, L=0.565)이 새 `--primary`(L=0.54)보다 **밝아서** 의미가 역전됐다.
게다가 `primary-strong` 은 원래도 틴트 표면에서 미달이었다(아래 3번).

램프를 정리했다:

```
--brand-700: oklch(0.54 0.195 32)   /* = #c72b10, D14 확정값 → --primary */
--brand-800: oklch(0.48 0.175 31)   /* = #aa210f, 신규 → --primary-strong */
```

`--ring` · `--chart-1` · `--sidebar-primary` · `--sidebar-ring` 도 `brand-600` → `brand-700`
으로 함께 옮겼다(전부 같은 시맨틱 역할을 참조하던 것들).

### 2. `--gradient-brand` 의 밝은 끝이 흰 텍스트에서 미달

`linear-gradient(135deg, brand-500, brand-700)` 이었는데 시작점 `brand-500` 은 흰 텍스트
대비 **2.78** 이었다. 135deg 는 좌상단→우하단이고 티켓 카드의 제목·본문이 바로 그
좌상단에 얹혀 있어서, 실제로 읽기 힘든 구간에 텍스트가 있었다.

경계를 탐색해 **L≈0.57 이 흰 본문(4.5) 통과선**임을 확인하고 양 끝 모두 통과하도록 바꿨다:

```
--gradient-brand: linear-gradient(135deg, oklch(0.57 0.21 34), oklch(0.46 0.17 27));
                                          /* 4.59 PASS */      /* 7.25 PASS */
```

### 3. `GuideNote`("세라")가 자기 카드 위에서 미달 — 거의 모든 화면에 있는 컴포넌트

`GuideNote` 는 `bg-primary/8` 틴트 표면에 `text-primary-strong` 으로 "세라"를 찍는다.
알파 합성까지 계산해 보니 기존 조합은 **3.93 FAIL** 이었다. 새 `primary-strong`(`#aa210f`)
으로 **5.60 PASS**. 이 컴포넌트는 홈·소개·티켓 등 대부분의 화면에 나오므로 영향 범위가 컸다.

### 4. `chats.tsx` — 흰 글씨를 밝은 코럴에 얹은 아바타

`from-coral-400 to-brand-400` 그라디언트에 `text-white` 였다. 대비 **1.73 ~ 2.12** —
큰 텍스트 기준(3.0)조차 크게 미달. `bg-gradient-brand` + `text-primary-foreground` 로 교체.
겸사겸사 컴포넌트에 남아 있던 마지막 raw 브랜드 토큰 사용도 사라졌다.

### 5. `chats.tsx` — 자기 색으로 틴트한 칩

"대화 중" 칩이 `bg-coral-600/10` 에 `text-coral-600` 이었다(같은 색을 배경과 글씨에 동시
사용 — 전형적인 함정). **4.32 FAIL** → `primary-strong` 조합으로 **6.03 PASS**.
`coral-600` 은 값이 옛 `brand-700` 과 완전히 중복이라 함께 걷어냈다.

### 6. 가짜 접속 상태 점 제거

아바타 우하단에 상태 점이 있었는데, 코드를 보면 **어떤 상태에도 연결되지 않은 무조건
렌더**였다. 스키마·API 어디에도 presence/online/last_seen 필드가 없다. 즉 이 제품에 없는
"지금 접속 중"이라는 신호를 시각적으로 주장하고 있었다.

색만 고치면 오히려 더 그럴듯한 거짓 신호가 되므로 제거했다.

### 7. 소개 화면에 DB enum id 가 그대로 노출

`intro.tsx` 가 흡연·음주를 `none` / `rare` 처럼 **원시 id 그대로** 찍고 있었다.
`me.tsx`(내 프로필)는 `SMOKING_OPTIONS.find(...)?.label` 로 한글 라벨을 매핑하는데
소개 화면만 빠져 있었다 — 상대를 판단하는 가장 중요한 화면이다. → "비흡연 / 가끔 한 잔".

### 8. 가격 미표기 (PRD F5 미충족)

PRD F5 가 명시적으로 요구한다:

> 화면에 **가격을 명시한다.** 현재 가격 문자열이 코드 전체에 0건이다

진단 당시와 똑같이 `grep` 결과 **여전히 0건**이었다. 30,000원을 받는 화면에 가격이 없는
것은 대비 문제보다 신뢰 문제다. `brand.ts` 에 표기용 단일 소스를 두고
(`MEETING_TICKET_PRICE_LABEL`) 티켓 카드 헤더와 하단 안내에 노출했다.

> 서버 권위 값은 `ticket_orders.amount` CHECK 와 `create_ticket_order()` 에 있다.
> 이 상수는 **표기 전용**이며 결제 금액의 근거가 아니다.

### 9. 금지 카피 2건 (현재는 죽은 코드)

`brand.ts` 의 `FEATURES` 에 PRD 가 금지한 표현이 남아 있었다:

- `"AI 인터뷰 프로필"` — 비목표: **"AI" 인터뷰 표기** / F2: 표기는 "인터뷰"
- `"만남 보장"` — F5·비목표: 절대어 대신 **환불 규칙을 명시**한다

단, `FEATURES` 는 **어디에서도 렌더되지 않는 죽은 export** 다(랜딩 `index.tsx` 는 자체
인라인 카피를 쓰고 그쪽은 깨끗하다). 그래서 **현재 사용자에게 노출되고 있지는 않다.**
그래도 랜딩을 다음에 배선하는 사람이 그대로 쓸 지뢰라서 카피를 고쳐 뒀다
("만남 보장" → 환불 규칙을 문장으로 명시).

# 타이포그래피 정리 (이어서)

컬러와 같은 방식으로 접근했다 — 눈으로 보고 판단하지 않고, **브라우저에서 실제로 어떤
서체가 렌더되는지 캔버스로 폭을 측정**해 확인했다.

## 발견 1 — 한 줄 안에서 서체가 갈라지고 있었다

`--font-sans` 의 첫 항목이 **Hind** 였다. Hind 는 데바나가리+라틴 서체로 **한글 글리프가
없다.** 그래서 같은 문장에서 라틴·숫자는 Hind, 한글은 Pretendard 로 갈라져 렌더됐다.

캔버스 실측 (16px 기준, 앱 스택 vs 각 서체 단독):

| 문자열      | 앱 스택 | Pretendard 단독 | Hind 단독 | 실제 렌더  |
| ----------- | ------- | --------------- | --------- | ---------- |
| `한글만`    | 41.48   | **41.48**       | 41.52     | Pretendard |
| `Abcdefg`   | 58.50   | 60.85           | **58.50** | **Hind**   |
| `30,000`    | 45.87   | 51.33           | **45.87** | **Hind**   |
| `MBTI ENFP` | 73.74   | 80.39           | **73.74** | **Hind**   |

즉 `"31 · 브랜드 디자이너"`, `"30,000원"`, `"MBTI ENFP"` 처럼 이 제품에 아주 흔한
한글+라틴 혼용 문자열이 전부 **두 서체로 쪼개져** 있었다. x-높이와 굵기 인상이 다르므로
같은 줄에서 어긋나 보인다.

**고침:** `--font-sans` 를 Pretendard 단독으로. Pretendard 는 Inter 계열 라틴을 한글과
함께 설계한 서체라 혼용이 자연스럽다. 수정 후 재측정 — 위 5개 문자열 전부 앱 스택 =
Pretendard 단독으로 **완전히 일치**.

## 발견 2 — 헤드라인의 한글/숫자 굵기 불일치

`.headline` 은 `font-family: var(--font-display)`(Archivo Black) + `font-weight: 700` +
`font-synthesis-weight: none` 이었다. 그런데 **Archivo Black 은 라틴 전용이고 굵기가
400 하나뿐**이다. 결과:

- 한글 → Pretendard **700**
- 숫자·라틴 → Archivo Black **400** (시각적으로는 ~900)

`home.tsx` 의 `"하나 31"` 이 정확히 이 케이스였다 — 이름은 Pretendard Bold, 나이 숫자는
Archivo Black. 이전 스크린샷에서 "31"이 유독 각져 보였던 이유다.

**고침:** 의도별로 토큰을 쪼갰다.

- `--font-display` → **Pretendard** (헤드라인. 한글·라틴·숫자가 한 서체로 나온다)
- `--font-wordmark` → **Archivo Black** (신규. 라틴만 쓰는 자리 전용)

`wordmark` 유틸리티를 만들어 실제로 라틴만 들어가는 두 곳에만 적용했다:
`Logo.tsx` 의 `"after"`, 랜딩 히어로 `"After Work Matching"`. 이 둘은 Archivo Black 이
브랜드 자산으로 잘 맞으므로 유지하는 게 맞다.

덤으로 `chats.tsx` 는 `.headline` 없이 `font-display` 만 써서 이름이 **굵기 700 이 아닌
기본 굵기**로 나오고 있었다(다른 모든 이름 표시와 불일치). `.headline` 으로 통일했다.

## 발견 3 — 로드만 하고 안 쓰는 서체

`Instrument Serif` 를 스타일시트로 받아오는데 **`font-serif` 사용처가 0건**이었다.
Hind(5웨이트)와 함께 제거 — 외부 폰트 스타일시트 3개 → 2개, Hind 5개 웨이트 파일과
Instrument Serif 파일이 더 이상 다운로드되지 않는다. 남은 건 Pretendard(가변,
동적 서브셋)와 Archivo Black(워드마크) 둘뿐이다.

## 발견 4 — 타입 스케일이 아니라 표류였다

우리 코드(vendored `src/components/ui/` 제외)에 **임의 폰트 크기가 24종 37회** 있었다.
문제는 종류가 많은 게 아니라 **서로 구분이 안 되는 값들**이었다:

- `0.6` `0.62` `0.65` `0.66` `0.68` `0.7` — 0.1rem 안에 6종
- `0.9` `0.92` `0.93` `0.95` `0.97` `1.0` `1.02` `1.05` `1.08` — 0.18rem 안에 9종

`0.92rem` 과 `0.93rem` 은 사람이 구분할 수 없다. 디자인 의도가 아니라 생성 과정에서
쌓인 표류다.

**고침:** Tailwind 기본 스텝(`xs .75` / `sm .875` / `base 1` / `lg 1.125` …)을 그대로 두고
— `text-sm` 이 이미 84회, `text-xs` 38회 쓰이므로 재정의하면 안 된다 — 그 **아래** 마이크로
단계만 신설했다:

```css
--text-3xs: 0.625rem; /* 10px — 아이브로우, 대문자 라벨 */
--text-2xs: 0.6875rem; /* 11px — 마이크로 캡션·칩 */
```

37회를 전부 스케일로 매핑했다. **본문 계열은 위로 올렸다** (`0.8`·`0.82` → `sm` 0.875):
한글은 같은 px 에서 라틴보다 읽기 어려우므로 13px 를 12px 로 내리는 건 잘못된 방향이다.
디스플레이 계열은 `1.7`/`1.9`/`2.1` 이 12% 씩만 벌어져 위계가 흐릿했는데
`2xl`(1.5)/`3xl`(1.875)/`4xl`(2.25)로 분명히 벌렸다.

결과 — 임의값 **0건**, 분포:

```
text-sm 84 · text-xs 38 · text-base 10 · text-2xs 10 · text-lg 7
text-3xs 6 · text-xl 4 · text-2xl 2 · 3xl·4xl·5xl·7xl 각 1~2
```

> **범위 주의:** `src/components/ui/*` 는 shadcn 원본 코드다. 거기 있는 `0.8rem` 4회는
> upstream 기본값이라 건드리지 않았다 — 우리 디자인 시스템이 아니고, 고치면 upstream
> 업데이트와 계속 충돌한다.

## 발견 5 — `<html lang="en">`

한국어 제품인데 `lang="en"` 이었다. `lang` 은 스크린리더 발음뿐 아니라 **CJK 줄바꿈
규칙과 폰트 선택**에 영향을 준다. `lang="ko"` 로 고쳤다.

## 검증

브라우저에서 재측정해 확인 — `lang="ko"` · Hind 미로드 · Instrument Serif 미로드 ·
Archivo Black 로드 유지 · 5개 문자열(혼용 포함) 전부 Pretendard 단독과 폭 일치.
화면 6개(랜딩·홈·소개·대화·티켓·나·온보딩) 육안 확인. `tsc` 클린 ·
`check:contrast` 통과 · pgTAP 14/14·12/12·7/7 회귀 없음.

# IA 재설계 (이어서)

## 진단 — 단건 도메인에 다건 UI 를 씌우고 있었다

이 제품은 **불변식 2**(동시 오픈 소개 ≤ 1) 때문에 진행 중인 일이 항상 정확히 하나다.
그런데 화면들이 "여러 개를 요약·나열하는" 패턴을 쓰고 있었다.

**홈** — 한 변수(퍼널 위치)를 네 곳이 서로 다른 문장으로 반복했다:

| 상태      | h1                        | 세라 카드                   | 진행바 | 다음 단계 |
| --------- | ------------------------- | --------------------------- | ------ | --------- |
| 대기      | 곧 소개를 보내드릴게요    | 지금은 기다리는 단계        | 0/4    | 전부 잠김 |
| 소개 도착 | 오늘 소개가 도착했어요    | 천천히 읽어보고 답해 주세요 | 0/4    | 1번 열림  |
| 응답 대기 | 상대의 답변을 기다리는 중 | 답이 오면 대화가 열립니다   | 1/4    | 1번 완료  |
| 대화 오픈 | 대화가 열렸어요           | 날짜와 장소만 정하면 됩니다 | 2/4    | 2번까지   |
| 만남 확정 | 만남이 잡혔어요           | 약속이 확정되었습니다       | 3/4    | 3번까지   |

게다가 진행바 라벨과 "다음 단계" 라벨이 서로 near-duplicate 였다.

**대화** — `/chats` 는 `<ul>` 인데 항목이 **최대 1개**였다(`getMyActiveMeeting()` 이 단건 반환).
대화를 열려면 의미 없는 탭이 한 번 더 필요했다.

## 고친 것

### 홈 — 대시보드 → 단일 액션 화면

- **"다음 단계" 리스트 제거.** 진행바를 리스트로 옮겨 적은 것이었다.
- **홈이 후보 카드를 렌더하지 않는다.** 상세는 `/intro` 담당 → 홈↔소개 탭 중복 해소.
  홈은 미리보기(이름·나이·직업·한 줄)와 진입 버튼만 갖는다.
- 상태마다 **카드 하나 + 액션 하나**로 통일.
- 진행바는 라벨 없이 얇게, `3/4 · 채팅 오픈` 한 줄로 축약.

**그리고 홈에 없던 정보를 넣었다** — 이게 재설계의 실질이다:

- **확정 상태**: 날짜·장소·상대 + **사적 대화가 열리는 시각**.
  지금까지 대화방 안 `MeetPlanner` 에 묻혀 있어 홈에서 알 수 없었다.
- **응답 대기 상태**: 24시간 환불 기한(P3) **실제 카운트다운**.
  기존엔 "24시간 안에 오지 않으면"이라는 정적 문구뿐이었다.

### 대화 — 탭이 곧 대화

`<Conversation>` 컴포넌트로 본문을 빼고 두 경로가 공유한다:

- `/chats` (탭) — 활성 만남의 대화를 바로 렌더. 목록 단계 제거.
- `/chat/$id` (딥링크·알림용) — 전체화면. 같은 본문.

앱 내부 이동은 전부 `/chats` 로 통일했다 — 대화가 항상 1건이라 id 를 들고 다닐 이유가 없다.
`bottomInset` prop 으로 탭바 유무에 따른 입력창 여백 차이만 처리한다.

### 소개 — 스펙을 아래로 (PRD F4)

브랜드가 "스펙 대신 결"을 선언했는데 스펙표(직업·지역·MBTI·흡연·음주·종교)가
히어로 바로 아래 최상단에 있었다. PRD F4 가 명시적으로 요구한 위계였는데 미구현이었다.

맨 아래로 내리고 `<details>` 로 접었다. 지우지는 않았다 — 판단에 필요한 정보이므로
원하면 펼쳐 본다. `<details>` 라 상태 관리 없이 동작하고 키보드·스크린리더도 기본 지원한다.
최종 순서: `소개 → 요즘 시간 쓰는 것 → 인터뷰 → 잘 맞는 사람 → 나누고 싶은 이야기 → 기본 정보(접힘)`.

### 나 — 프로필 미리보기 + 설정

- **"홈으로" 버튼 제거.** 탭바에 홈이 있는데 나 탭의 primary CTA 가 홈 이동이었다.
- `<ProfileDetail>` 을 소개 화면과 공유하는 이유를 문장으로 밝혔다 —
  "소개가 열린 상대에게는 아래 그대로 보입니다."
- **약관·개인정보 처리방침 링크 추가.** 그전까지는 **가입 화면에서만** 접근 가능해서,
  가입 후에는 자신이 동의한 내용을 다시 볼 방법이 없었다.

### 탭 — 라벨을 성별에 맞춤

4개는 유지하되(하트 아이콘 유지) 두 번째 탭 라벨을 **여성 "평가" / 남성 "소개"** 로 나눴다.
같은 화면이지만 하는 일이 다르다 — 여성은 남성 프로필을 계속 평가하는 반복 활동이고
(큐가 계속 있다), 남성은 자신에게 온 소개 한 건을 읽는다. 하나로 뭉뚱그리면 여성 쪽에서
"소개"의 뜻이 어긋난다.

### 세라 — 정체 고지 (PRD F6)

"세라가 누군지 모르겠다"는 사용자 피드백이 있었는데, 확인해보니 PRD F6 이 이미 요구한
사항이었고 구현이 0건이었다(`세라의 정체를 결제 전에 한 문장으로 밝힌다`).

틴트 8%→12%, 강조선·아바타 확대로 눈에 띄게 하고, `세라 · 자동 안내` 뱃지와 한 줄 설명을
붙였다. 노출 지점은 홈(첫 만남)과 **티켓 결제 직전** — F6 이 지정한 위치다.
아바타는 사람 일러스트로 교체할 수 있게 `<span>` 하나로 분리해 뒀다.

## 검증

`tsc` 클린 · `lint` 0/0 · `check:contrast` 전부 통과 · pgTAP 14/12/7/6 ·
임의 폰트 크기 0건 유지 · 남녀 계정 양쪽 실제 로그인해 화면 확인.

> 스크린샷으로 "비활성 버튼이 회색이다", "프로필 섹션이 흐리다" 두 번 의심했는데,
> computed style 을 실측하니 둘 다 **전환 애니메이션 중간이 찍힌 것**이었고 실제 결함이
> 아니었다. 안 고쳐도 되는 것을 고치지 않았다.

## 손대지 않은 것

- **다크 모드** — PRD 비목표(토글이 없어 노출되지 않음). `.dark` 블록은 남아 있으나
  브랜드 컬러가 아닌 값들(cyan 계열 `--shadow-brand` 등)이 섞여 있어 실제로 켜면 깨진다.
  켜기로 결정하면 그때 전면 정리 대상.
- **`--gradient-warm`** — 죽은 토큰(사용처 0건). 지우지 않고 남겼다.
- **결제 체크아웃 UI** — 실제 토스 가맹점 키 부재로 블로킹(S5 참조).
