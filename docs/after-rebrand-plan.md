# 애프터 리브랜딩 설계안과 구현 계획

작성일 2026-10-05. 기준 코드 `718df70`. 대상은 제품 책임자와 후속 구현 모델 `gpt-6.0 luna high`다. 서비스명은 **애프터**, 영문 표기는 **after**로 통일한다. 이 문서는 구현을 위한 디자인 기준이며, 작성 시점에는 제품 코드와 운영 설정을 바꾸지 않았다.

브랜드 방향은 **퇴근 후, 한 사람과의 약속.**이다. 회사와 가까운 생활권에서 실제로 만날 의사가 있는 직장인이 탐색과 일정 조율에 쓰는 수고를 줄이는 서비스로 표현한다. 따뜻한 종이색, 짙은 잉크색, 절제된 살구색으로 평일 저녁의 기대감을 만든다.

## 제품이 전달할 약속

첫 고객은 만날 시간은 있지만 상대를 탐색하고 약속을 조율하는 데 피로를 느끼는 직장인이다. 첫 운영 권역은 강남·역삼권이며, 지역은 가입 가능 범위로 표시한다. 브랜드 이름과 기본 슬로건에는 고정하지 않는다.

| 제품의 가치            | 화면에서 보여줄 근거                              | 표현 기준                                          |
| ---------------------- | ------------------------------------------------- | -------------------------------------------------- |
| 상대를 이해하기 쉬움   | 본인이 확인한 소개글, 관심사, 대화 주제           | AI가 작성한 초안은 이용자가 확인·수정한다          |
| 선택에 드는 수고 감소  | 한 번에 한 사람의 프로필과 분명한 다음 행동       | 무한 탐색·외모 점수·상대 등급을 연상시키지 않는다  |
| 만남으로 이어지는 과정 | 요청, 응답, 일정 제안, 확정 상태                  | 아직 정해지지 않은 약속을 확정으로 표현하지 않는다 |
| 운영에 대한 신뢰       | 회사 이메일 인증, 사진 검수, 신고·차단, 지원 창구 | 현재 확인한 범위만 표시한다                        |

회사 이메일 인증을 정부 신분증 본인인증이나 소개 내용 전체의 사실 보증으로 확대해 표현하지 않는다. AI 적합도, 만남 성사, 특정 기간 내 소개도 실제 근거 없이 보장하지 않는다. 신원·사실성 검증을 강화하는 기존 백로그는 계속 별도 관리한다.

이름은 애프터선셋·애프터워크로 확장하지 않는다. 워드마크 외 본문, 메일 제목, 접근성 레이블은 한글 이름을 사용한다. `BRAND.name`, `BRAND.nameEn`, `BRAND.tagline`, `BRAND.description`을 화면의 기준으로 삼는다. 별도로 번들되는 Supabase 함수와 인증 템플릿은 동일 표기를 따로 동기화한다.

기존 제안인 “퇴근 후, 만날 사람만.”은 사용하지 않는다. 즉시 만날 수 있는 사람만 가입했다는 인상과 배제적인 말투를 피한다. “평가할 프로필”은 “살펴볼 소개”로, “회원님을 먼저 좋다고 한 분”은 상태 중심 문장으로 바꾼다. 성별에 따른 실제 매칭 규칙은 유지한다.

해외에 `After: Meet & Date`라는 앱이 있다는 점은 이전 조사에서 확인됐다. 한글명과 설명어를 붙인다고 이름 충돌이 해소되는 것은 아니다. 스토어 등록 가능 여부와 국내 상표 확인은 출시 전 별도 항목이며, 이 문서는 권리 확보를 확인한 문서가 아니다. 참고: [After 앱스토어 페이지](https://apps.apple.com/us/app/after-meet-date/id1614909414).

## 시각 디자인

### 전체 인상

낮에는 편안한 종이, 저녁에는 차분한 잉크색으로 읽히는 제품이다. 넓은 여백과 읽기 좋은 소개글, 예약 확인서처럼 명료한 약속 카드가 인상을 만든다. 색을 제외한 여백·타입·카드 구조는 명암 테마에서 동일하게 유지한다.

밝은 화면에서는 중립 표면이 대부분을 차지하고, 잉크색은 글자와 주요 버튼에, 살구색은 로고 포인트·선택 상태·작은 강조 면에 사용한다. 살구색으로 전체 배경이나 소개글 카드를 채우지 않는다. 금속 금색, 별·달·일식, 하트 패턴, 반짝이는 AI 장식, 성별별 분홍/파랑 구분은 사용하지 않는다.

`accent`는 공용 컴포넌트의 hover 배경에도 쓰이므로 중립 색으로 둔다. 브랜드용 살구색은 별도 토큰으로 명명한다. 성공·주의·위험은 아이콘과 문장을 함께 써서 색만으로 상태를 구별하지 않는다. 내 말풍선·선택 카드의 글자색을 `primary-foreground`에 무조건 연결하면 라이트에서 흰 글자가 올라갈 수 있으므로 역할별로 지정한다.

주요 조합의 sRGB 상대 명도 대비를 설계 시 계산했다: 잉크/종이 **13.21:1**, 흰색/잉크 버튼 **14.39:1**, 보조 글자/종이 **5.01:1**, 잉크/살구 **5.24:1**, 강조 글자/살구 틴트 **4.78:1**, 다크 본문/배경 **13.94:1**. 이것은 기본 불투명 조합의 계산이며 실제 CSS 변환, 투명도, hover, disabled, 포커스, 입력 경계까지 검증했다는 뜻은 아니다.

기존 브랜드 그라디언트는 일반 버튼·티켓·아바타에서 단색으로 정리한다. 불필요해진 `gradient-brand`를 제거하면 검사 스크립트의 필수 파싱도 함께 수정한다. 검사의 대비 기준을 낮춰 통과시키지 않는다. `brand-*`, `peach-*`, `ink`, `surface` 등 기존 별칭은 사용처를 확인한 뒤 새 토큰에 연결하거나 제거한다. 차트·사이드바·알림·포커스까지 같은 체계를 적용한다.

### 로고와 앱 아이콘

기본은 **소문자 after 워드마크**다. Pretendard의 라틴 글자를 기반으로 600~650 굵기, 자간 약 -0.035em의 단정한 형태를 사용한다. 우선 글자를 변형하지 않은 버전으로 크기와 균형을 검증한다. 화면 헤더 높이 24px 전후에서도 읽혀야 한다. 앱 전체 본문과 한글은 Pretendard를 유지한다.

보조 심벌은 같은 글꼴의 **소문자 a 한 글자와 우상단의 작은 살구색 점**이다. 점은 알림 상태가 아니라 심벌 일부이고, UI 알림 배지와 혼용하지 않는다. 아이콘 배경은 잉크색, a는 종이색으로 사용한다. 글자 높이는 캔버스의 약 55%, 외곽 안전 여백은 최소 16%를 기준으로 광학 보정한다. 16px 파비콘에서는 점을 생략하고 a의 실루엣을 우선한다.

워드마크와 심벌은 SVG로 관리한다. 앱 아이콘용 글자는 경로로 변환해 렌더 환경의 폰트 설치 여부에 영향을 받지 않게 한다. SVG를 원본으로 PNG·ICO·iOS 자산을 일관되게 생성한다. 앱스토어 아이콘은 불투명 1024px 정사각형으로 만든다. 사진형 로고나 래스터 생성 모델은 필요하지 않다.

완료 기준은 16·24·32·64px에서 a가 읽히고, 1024px에서는 윤곽과 여백이 깨끗한 것이다. 사용자에게 보이는 한글 표기는 계속 애프터이며 영문 그림만으로 서비스명을 전달하지 않는다.

### 타이포와 컴포넌트

- 본문 16px/1.6, 보조 설명 14px/1.5, 작은 레이블 12px 이상. 약관·기한·티켓 조건을 작은 회색 글자로 숨기지 않는다.
- 랜딩 제목 32~~40px, 화면 제목 24~~28px, 카드 제목 18~20px. 한국어 글자 간격을 과하게 좁히지 않는다.
- 화면 좌우 여백 20~24px, 기본 간격 단위 4px. 카드 내부 여백 20px, 카드 반경 16px, 버튼·입력 반경 12px를 기본으로 한다.
- 주요 버튼 높이 52px, 보조 조작 영역 최소 44px. 문구는 동사와 대상이 드러나게 쓴다.
- 그림자는 얕게 유지한다. 선택·오류·키보드 포커스는 그림자 외에도 테두리와 아이콘으로 구분한다.
- 짧은 상태 전환은 150~220ms. 랜딩의 현재 560ms 대기와 화면 전체 원형 확대 전환은 제거하고 즉시 가입으로 이동한다. 모션 감소 설정을 존중한다.
- Fraunces·Archivo Black은 실제 사용처를 먼저 조사한다. 새 디자인에 필요하지 않은 폰트 요청과 클래스만 제거한다.

## 화면별 설계

### 랜딩과 로그인

랜딩 첫 화면은 로고, 2줄 제목, 짧은 설명, 현재 운영 권역, 주요 버튼으로 구성한다. 헤더에 중복된 시작 버튼을 두지 않고 로그인 링크만 남긴다. 화면 높이가 짧거나 글자가 커지면 본문을 스크롤할 수 있어야 한다.

```text
after                                  로그인

퇴근 후,
한 사람과의 약속.

회사 이메일을 인증한 직장인을
한 번에 한 사람씩 소개해요.

현재 강남·역삼권에서 운영해요.

[                 시작하기                 ]
고객 지원 · 개인정보 처리방침 · 계정 삭제
```

실제 동작 예시가 필요하면 제목 아래 약속 카드 1개만 넣고 **화면 예시**라고 표시한다. 가상의 약속을 현재 사용자에게 도착한 소개처럼 보이게 하지 않는다. 로그인 화면은 입력과 오류 복구에 집중하며, 앱의 이메일/비밀번호 로그인과 웹의 기존 카카오 경로를 유지한다.

### 가입과 소개글

단계와 진행 상태를 간결하게 표시한다. 취향 문답은 가입 과정에서 완료하고, 홈에서 다시 숙제처럼 제시하지 않는다. AI 초안 화면의 “이렇게 소개해도 될까요?”와 수정 기능을 유지하며, 생성 실패·재시도·입력 보존도 기존 동작을 지킨다. 로딩에 궁합 점수나 가상의 분석 단계를 추가하지 않는다.

### 홈

홈의 기본 구조는 **상태 제목 하나 → 핵심 카드 하나 → 주요 행동 하나**다. 안전·권한·오류 안내가 필요할 때에는 추가할 수 있지만, 같은 상태를 제목과 안내 카드에서 두 번 길게 설명하지 않는다.

| 실제 상태                | 제목과 카드 내용                                         | 주요 행동                                            |
| ------------------------ | -------------------------------------------------------- | ---------------------------------------------------- |
| 프로필 완료 후 소개 대기 | 소개를 준비하고 있어요 / 새 소개가 도착하면 알려드릴게요 | 알림 미설정 때만 알림 설정; 설정됨이면 억지 CTA 없음 |
| 소개 잠시 중단           | 소개를 잠시 쉬고 있어요                                  | 소개 다시 받기                                       |
| 열 수 있는 소개 도착     | 새로운 소개가 도착했어요                                 | 소개 보기                                            |
| 여성이 살펴볼 후보 있음  | 새로운 소개가 도착했어요                                 | 소개 보기                                            |
| 상대 응답 대기           | 답변을 기다리고 있어요 / 실제 응답 기한                  | 요청 보기                                            |
| 일정 제안 필요           | 만날 시간을 정해볼까요?                                  | 가능한 시간 보내기                                   |
| 상대 일정 중 선택 가능   | 가능한 시간이 도착했어요                                 | 일정 확인하기                                        |
| 만남 확정                | 약속이 정해졌어요 / 실제 날짜·시간·장소·상대             | 약속 보기                                            |

문구는 기존 서버 상태에 연결한다. 대기 중에는 임의의 도착 예정일이나 진행률을 보여주지 않는다. 일정 전달 후 대기와 상대 일정 선택 가능 상태는 실제 필드와 사용자 역할에 맞춰 분기한다. 무료 베타에서 티켓이 없는 경우 현재 `home.tsx`에 남은 “소개 티켓 사기”를 운영자 발급 안내로 연결하고, 유료 모드에서는 실제 가격·소모 규칙을 유지한다.

### 소개와 약속

소개 상세는 이름·나이·직업 다음에 한 줄 소개와 소개글을 충분히 읽을 수 있게 배치한다. 태그는 소개글 아래에 묶고 관심사·대화 주제를 펼쳐볼 수 있게 한다. 사진을 확대해 글을 아래로 밀어내거나 프로필 카드를 스와이프 덱으로 바꾸지 않는다. 신고·차단 메뉴는 쉽게 찾을 수 있는 자리에 유지한다.

약속 카드는 사람, 날짜, 시간, 장소 순서로 읽히게 한다. 미정 값은 “미정”으로 표시한다. 확정된 정보와 필요한 다음 행동을 한곳에 모으고, 연락·취소·신고 경로는 기존 권한과 처리 규칙을 따른다. 새 달력 기능이나 예약 기능은 이번 범위에 넣지 않는다.

### 안내와 나머지 화면

`세라 · 자동 안내`는 `애프터 자동 안내`로 정리한다. 실제 운영자와 자동 안내가 같은 발화자로 보이지 않게 한다. 채팅 내 시스템 문구·소개 화면·티켓 화면의 관련 노출도 함께 조사한다. 기존의 비인간 안내 고지는 간결하게 유지한다.

내 프로필·설정·티켓·지원·계정 삭제·약관 화면에는 같은 글자·색·버튼 체계를 적용한다. 어드민은 기존 메뉴와 업무 밀도를 유지하고 브랜드 헤더·색 토큰·상태 표시만 맞춘다. 운영 효율 개편이나 매칭 알고리즘 변경은 이번 리브랜딩과 섞지 않는다.

### 기술 식별자와 도메인

`kr.eclps.app` 번들 ID·URL 스킴, Cloudflare Worker 이름 `eclipse`, Supabase 프로젝트 ID, 기존 계정 이메일·인증키는 전체 문자열 치환 대상에서 제외한다. 브랜드 개편만을 이유로 별도 앱·Worker·DB를 만들면 배포와 인증 연속성을 잃을 수 있다. 기존 로그인·계정·딥링크·메일 인증 동작을 보존하고 고객에게 보이는 표시명을 바꾼다.

`eclps.kr`은 현재 운영 주소이며 새 도메인은 아직 선택·소유 확인되지 않았다. 새 도메인이 준비되기 전에도 앱과 웹의 표시명·디자인 구현은 진행할 수 있다. 그동안 화면은 애프터지만 링크와 발신 주소에는 기존 도메인이 남는다는 전환 상태를 작업 보고서에 적는다. 이를 도메인까지 완료한 리브랜딩으로 보고하지 않는다.

새 도메인 전환은 소유 확인 후 별도 배포 단계로 수행한다.

1. 새 도메인을 기존 서비스에 연결하고 TLS·경로·지원·삭제 페이지를 확인한다.
2. 웹 Auth 허용 주소, Site URL, 카카오 등록 주소, 알림 링크 환경값, canonical·OG URL, 배포 검증 URL을 조사해 양쪽 주소를 지원하게 한다.
3. 신규 도메인에서 이메일 코드·비밀번호·웹 OAuth·계정 복구 흐름을 검증한다. 다른 origin의 기존 웹 세션은 자동 이전된다고 가정하지 않는다.
4. 발신 도메인을 바꿀 경우 실제 DNS·메일 공급자 인증을 완료한 뒤 전환한다. 수신 가능한 문의 주소는 새 수신함이 확인되기 전까지 유지한다.
5. 새 도메인을 기본으로 바꾸고 기존 주소의 경로·쿼리를 보존해 리다이렉트한다. 미사용 인증 링크와 웹 OAuth 왕복이 깨지지 않는지 검증하고, 필요하면 인증 경로는 전환 기간 동안 유지한다.
6. 기존 도메인과 인증된 발신 주소는 유입·로그인 문제가 없는 것을 확인하기 전까지 유지한다. 전환 오류 시 원래 주소로 복구할 수 있게 한다.

R1~R4는 하나의 작업 브랜치 `codex/after-rebrand`에서 단계별 커밋으로 진행하고, 서로 의존하는 이름·로고·색·메일 수정은 하나의 제품 릴리스로 병합한다. R6가 준비되어 있으면 함께 전환하고, 아니면 별도 PR로 처리한다. 심사용 계정은 기존 것을 재사용하며 단순 리브랜딩 때문에 새로 만들거나 초기화하지 않는다.

현재 자동 배포 워크플로는 `CLOUDFLARE_DEPLOY_ENABLED == true` 조건을 사용한다. 직전 작업에서는 비활성화되어 있었다. 실제 병합 시 현재 상태를 다시 확인하고, 배포가 건너뛰어지면 인증된 기존 배포 경로로 병합된 커밋을 배포한다. 웹 배포만으로 Supabase 함수·Auth 템플릿·App Store Connect 변경까지 반영됐다고 가정하지 않는다.

## 검증과 완료 판정

기계 검사는 `npm run check`, `npm run build:app`, `npx cap sync ios`, `git diff --check`와 저장소 릴리스 게이트를 따른다. 코드가 변경되면 변경 부분을 보안·품질·성능·유지보수 관점에서 리뷰한다. DB·Auth 동작이 달라진 부분만 해당 회귀 검증을 추가한다. DB 테스트를 위해 운영 데이터를 초기화하지 않는다.

시각 확인은 너비 320·390·430px와 데스크톱 프레임, 라이트·다크에서 수행한다. 키보드가 열린 로그인·가입·채팅, 큰 글자, 빈 상태·오류·로딩·긴 소개글, 스크롤과 안전영역을 확인한다. 로고 16·24px 식별성, 버튼·선택·오류·포커스 대비도 기록한다. CSS 기본색 계산 통과만으로 화면 검증을 대체하지 않는다.

남녀 각각 소개 없음·소개 도착·상대 응답 대기·일정 조율·약속 확정·소개 중단 상태를 확인한다. 사진 검수 중 상태와 프로필 초안 생성 실패도 유지되는지 확인한다. 홈의 중복 안내, 무료 베타의 구매 유도, 실제 필드와 맞지 않는 상태 문구가 없어야 한다.

메일 검증은 로컬 수신함 또는 본인이 통제하는 테스트 계정으로만 수행한다. 일반 회원에게 리브랜딩 공지나 시험 메일을 일괄 발송하지 않는다. 스토어 스크린샷은 새 앱 빌드와 동일한 기능·카피를 보여야 하며 실제 고객의 개인정보를 사용하지 않는다. 기존 스크린샷의 카카오 로그인 노출 설명은 현재 iOS 빌드와 맞춰 정리한다. 업로드 규격은 제출 시점의 콘솔 요구값으로 확인한다.

사용자에게 보이는 이전 이름을 검색해 남은 항목을 분류한다. 기술 식별자, 유지 중인 도메인, 과거 기록, 기존 계정은 사유를 남기고 허용한다. 특히 로고 하드코딩, 지원 메일 제목, `og:site_name`, OTP 제목, 운영 SMTP 표시명, 네이티브 스플래시가 빠지지 않아야 한다.

최종 보고에는 변경 PR·운영 버전·검증 화면·메일 확인 결과와 도메인/스토어 등 미완료 항목을 적는다. 접근 권한이나 도메인 선택이 필요한 경우 해당 접점만 보류하고 이미 가능한 구현과 검증은 마친다. 이름 충돌 확인, 기존 법률·본인인증·PG 백로그, 실기기 확인을 완료한 것으로 추정하지 않는다.

## 구현 모델에 전달할 요청
