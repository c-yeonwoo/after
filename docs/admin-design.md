# 운영자 페이지 설계

작성 2026-08-09. **구현 완료 — 2026-08-11.** §5 의 세 단계를 모두 마쳤고,
설계에 없던 것(사진 검수)이 하나 늘었다.

| 단계 | 마이그레이션 | 화면 |
|---|---|---|
| 1 뼈대 · 신고 | `s16` `s16b` `s16c` | `/admin` `/admin/reports` |
| 2 큐레이션 | `s19` `s20` `s20b` | `/admin/curation` |
| 3 회원 · 만남 | `s17` `s17b` | `/admin/members` `/admin/meetings` |
| — 사진 검수 (신규) | `s18` | `/admin/photos` |

---

## 0. 왜 필요한가

지금 이 서비스에 **운영자가 개입할 수 있는 지점이 하나도 없다.** 코드에 role 개념
자체가 없고, 라우트 20개가 전부 사용자용이다.

그런데 운영자가 있어야만 되는 일이 이미 쌓여 있다.

| 일 | 지금 어떻게 되나 |
|---|---|
| 콘텐츠 신고 처리 | `resolve_content_report()` 를 만들 예정인데 **부를 화면이 없다** |
| 노쇼 신고 검토 | 자동 판정(인정/무응답)만 있다. 다툼이 생기면 손댈 수 없다 |
| 회원 정지·해제 | `account_state` 를 SQL 로 직접 바꿔야 한다 |
| 환불 | `refund_ticket()` 이 있지만 부를 사람이 없다 |
| 지표 확인 | Supabase 대시보드에서 SQL 을 매번 짠다 |
| **콜드 스타트** | 아래 §3 참고 — 가장 큰 문제다 |

## 1. 매칭은 이미 자동이다 — 그런데 그게 문제다

먼저 사실 확인. "매칭을 붙여주는 어드민"이 빠진 게 아니라, **설계상 운영자가 낄
자리가 없게 되어 있다.**

```
① 여성이 next_candidate() 로 남성 후보를 받아 like / pass
② 남성이 open_intro() 를 부르면
   → "나에게 like 를 준 여성" 중에서 한 명이 열린다
   → 없으면 P0002 'no eligible candidate'
③ 남성이 티켓 사용 → 만남 요청
④ 여성이 선호 응답 → 대화 오픈
⑤ 날짜 확정
```

`open_intro()` 는 `authenticated` 권한이고 **사용자 본인이 클라이언트에서
호출한다**(`src/lib/api.ts:317`). 서버가 밀어주는 게 아니다.

### 이 구조의 불변식

> **남성은 자신을 먼저 좋다고 한 여성만 본다.**

이건 우연이 아니라 제품의 근간이다. 3만원을 정당화하는 근거이고, 화면에도 그대로
노출된다 — *"이분이 먼저 회원님을 좋다고 하셨어요."*

**운영자 기능을 설계할 때 이 불변식을 깨는지가 가장 중요한 판단 기준이다.**

## 2. 결정해야 하는 것

### D1. 어드민을 어디에 두나 — `after` 만의 제약

palette 는 SPA 하나라 `/admin` pathname 분기로 끝났다(ADR 0006). 여기는
**빌드 타깃이 둘**이라 그대로 못 쓴다.

```
npm run build      웹 — Nitro/Cloudflare  ← 어드민은 여기만
npm run build:app  앱 — SPA 셸 → Capacitor 번들  ← 어드민이 들어가면 안 된다
```

앱 번들에 어드민 코드가 섞이면 번들이 커지고, 심사에서 "숨은 기능"으로 오해받을
여지도 생긴다.

| 옵션 | 평가 |
|---|---|
| **A. `/admin/*` 라우트 + 앱 빌드에서 제외** | ✅ 배포 단위 하나 유지. `BUILD_TARGET=app` 일 때 라우트를 빌드에서 빼면 된다 |
| B. 별도 레포·배포 | 운영 복잡도↑. 타입·RPC 를 두 벌 관리 |
| C. Supabase Studio + SQL 만 | 코드 0 이지만 신고 처리·수동 매칭을 매번 손으로 짜야 한다 |

→ **A 추천.**

### D2. 권한 모델 — RLS 로 강제해야 한다

이 앱의 보안 모델은 RLS 다("정책 없음 = 불가능"). 어드민 권한도 예외가 아니다.
프론트에서 화면만 가리는 방식은 여기서 통하지 않는다 — 클라이언트가 PostgREST 를
직접 부르기 때문이다.

```sql
profiles.role  member | admin   (기본 member)

is_admin() → boolean             -- SECURITY DEFINER, search_path 고정
                                 -- 정책 서브쿼리가 profiles RLS 를 다시 타는 것을 피한다
                                 -- (S8 에서 affinities 가 같은 함정에 빠졌었다)
```

모든 어드민 조회·조작 정책은 `is_admin()` 을 통과해야 한다. 어드민 RPC 도 마찬가지다.

### D3. 어드민 로그인 — 같은 OTP 로 충분한가

palette 는 별도 로그인 경로를 뒀다(audit 분리·실수 방지). 여기는 로그인이 회사
이메일 OTP 하나뿐이라 **같은 로그인을 쓰되 `/admin` 진입 시 `is_admin()` 을
확인**하는 게 단순하다. 어드민도 회사 이메일이 있는 사람이다.

다만 **어드민 계정은 일반 회원 프로필과 겸하지 않는 게 좋다** — 운영자가 자기
소개를 받는 상황이 섞이면 데이터가 지저분해진다.

### D4. 매칭에 운영자가 어떻게 개입하나 — **결정됨**

> **운영자 큐레이션이 매칭의 필수 경로가 된다.** 자세한 것은
> [`docs/intro-flow-v2.md`](./intro-flow-v2.md) 에 따로 정리했다.

여성의 like 가 곧바로 소개가 되지 않는다. 운영자가 어드민에서 남성을 조회해
**그를 좋다고 한 여성 카드 리스트**를 보고, 정렬해서 그 남성의 **소개 큐**를
만든다. 남성은 "소개 받기" 가 ON 이고 큐에 카드가 있을 때만 소개를 받는다.

**불변식은 유지된다** — 큐를 만들 수 있는 풀 자체가 "나를 좋다고 한 여성" 이므로
*"이분이 먼저 회원님을 좋다고 하셨어요"* 는 여전히 참이다.

이 결정의 대가:

- **운영자가 매칭의 단일 실패점이 된다.** 순수 큐레이션이라 자동 폴백이 없다.
- **소개 열람이 유료(5,000원)가 되면서 큐레이션 품질이 곧 CS 부하가 된다.**

→ 대시보드가 이 둘을 숫자로 보여줘야 한다(§4).

## 3. 데이터 모델

```sql
-- 역할
alter table profiles add column role text not null default 'member'
  check (role in ('member','admin'));

-- 운영자 개입 기록 — 모든 강제 조작은 사유가 남는다
create table admin_actions (
  id          uuid primary key default gen_random_uuid(),
  actor_id    uuid not null references profiles(id),
  kind        text not null,          -- ban | unban | refund | resolve_report | boost | cancel_meeting
  target_user uuid references profiles(id),
  target_ref  uuid,                   -- meeting_id · report_id 등
  note        text not null,          -- **필수** (palette ADR 0012 의 교훈)
  created_at  timestamptz not null default now()
);

```

소개 큐(`intro_queue`)와 소개 티켓은 [`intro-flow-v2.md`](./intro-flow-v2.md) §3
에 있다 — 어드민만의 것이 아니라 사용자 흐름까지 걸치는 모델이라 그쪽에 뒀다.

## 4. 화면 `구현`

`/admin` 아래 중첩 라우트 다섯 탭. 앱 빌드에서는 `admin.` 접두사로 제외된다
(D1) — 라우트 파일명을 바꿀 때 이 규칙을 깨면 어드민이 앱 번들에 섞인다.

| 탭 | 경로 | 내용 |
|---|---|---|
| **대시보드** | `/admin` | 아래 지표. 숫자를 누르면 그 모집단의 목록으로 간다 |
| **큐레이션** | `/admin/curation` | 작업 대상 목록(큐 빈 사람부터) → like 풀 → 순서 정해 큐 저장 |
| **회원** | `/admin/members` | 목록(성별·상태·권역·쉬는중 + 이름/메일 검색) → 상세 → 정지/해제 |
| **사진 검수** | `/admin/photos` | 격자로 깔고 그 자리에서 승인·반려 (설계에 없던 것) |
| **신고** | `/admin/reports` | 콘텐츠 신고. 인정/기각 + 사유 필수 → 인정 시 환불 |
| **만남** | `/admin/meetings` | 상태 필터 목록 · 강제 취소(사유 필수) · 환불 |

모든 조작에 **사유(note) 필수**. `admin_actions` 에 남고, 처리 목록에서 그 사유를
**되읽을 수 있어야 한다** — s16c 에서 강제만 하고 보여주지 않던 것을 고쳤다.

**목록은 표로 눕힌다.** 처음엔 카드로 쌓았는데 한 화면에 다섯 건밖에 안 들어와서
"뭐가 밀려 있나" 를 훑을 수 없었다. 훑기와 처리를 나눠 한 건만 펼친다. 사진 검수는
예외다 — 사진 자체가 판단 근거라 격자로 깔아야 한다.

**회원 상세는 사용자가 보는 프로필을 그대로 그린다.** 정의 목록으로 늘어놓으면
"이 사람이 어떻게 보이나" 를 판단할 수 없는데, 신고 판정과 큐레이션이 결국 그
판단이다. 사용자 화면과 같은 `<ProfileDetail>` 을 쓴다.

**노쇼 신고 화면은 아직 없다.** 위 표의 "신고" 는 콘텐츠 신고만이다 — §6 참고.

### 대시보드가 반드시 보여줘야 하는 것

일반적인 KPI(가입·활성·성사)보다 **이 두 묶음이 먼저다.** v2 에서 운영자가
병목이자 품질의 원천이 되기 때문이다.

**적체 — 운영자가 밀리고 있는가**
- 큐레이션 대기 중인 like 수 → `backlog.unmatched_likes`
- 큐가 빈 활성 남성 수 → `backlog.starved_males`
- 가장 오래 기다린 like 의 경과 시간 → `backlog.oldest_like_hours`
- **`구현`** 사진 검수 대기 → `backlog.pending_photos`. 검수 전 후보 풀에서
  빼기로 했으므로(s18) 이 숫자가 곧 **지금 아무에게도 보이지 않는 회원 수** 다

**품질 — 큐레이션이 좋은가**
- 소개 넘김 비율 → `quality.intros_passed / intros_total`
- 열람 → 만남 전환 → `quality.intros_used`
- **`구현`** 큐레이션 노동 회수율 → `cards_delivered` · `cards_opened` ·
  `cards_expired`

패스율이 없으면 품질을 관리할 방법이 없고, 적체 지표가 없으면 사람이 병목이라는
사실이 숫자로 안 보인다.

**아직 없는 것: 큐레이터별 패스율.** `intro_queue.curated_by` 는 기록하고 있으니
집계만 붙이면 된다. 운영자가 한 명인 동안은 전체 값과 같아서 미뤘다.

## 5. 단계 `구현`

콜드 스타트와 심사 대응이 급하니 그 순서로 자른다.

**실제 순서는 1 → 3 → 사진 검수 → 2 였다.** 2단계(큐레이션)가 가장 크고 위험해서
그 앞에 티켓 종류를 먼저 붙였고(지뢰 제거), 회원·만남 통제는 사용자 흐름을 건드리지
않아 먼저 넣어 운영자가 쓸 수 있는 것을 빨리 만들었다.

**1단계 — 뼈대와 신고 처리**
`role` 컬럼 · `is_admin()` · RLS 정책 · `/admin` 라우트(앱 빌드 제외) · 대시보드 ·
신고 처리. **UGC 신고·차단(s16)과 짝이라 같이 가야 의미가 있다.**

**2단계 — 큐레이션** ← v2 흐름의 핵심
`intro_queue` · 소개 티켓 · `open_intro()` 재작성 · 남성 "소개 받기" 토글 ·
어드민 큐레이션 화면. [`intro-flow-v2.md`](./intro-flow-v2.md) 참고.

이 단계가 **가장 크고 가장 위험하다** — `open_intro()` 를 재작성하고 티켓에
종류를 붙이므로 pgTAP·홈·상점이 함께 움직인다.

**3단계 — 회원·만남**
회원 목록/상세/정지, 만남 강제 취소·환불.

## 6. 열린 질문

- **어드민 계정을 어떻게 만드나** — 첫 어드민은 SQL 로 심을 수밖에 없다(seed.sql
  이 그렇게 한다). 그 뒤로는 어드민이 어드민을 임명하는 구조로 갈지. 아직 화면이
  없다 — `admin_set_account_state` 는 운영자 계정을 아예 거절한다(마지막 운영자를
  정지시키면 아무도 못 들어온다).
- **audit 보존 기간** — `admin_actions` 를 영구 보관할지. 지금은 무제한이다.
- **2단계 인증** — 어드민에게 추가 인증을 요구할지. 지금은 OTP 하나뿐이라
  회사 메일이 뚫리면 어드민도 뚫린다. **미해결.**
- **`admin_member_detail` 이 프로필 전체를 낸다** — `to_jsonb(profiles)` 라
  컬럼이 늘 때 함수를 고칠 필요가 없는 대신, 민감 컬럼이 붙으면 그대로 새어
  나간다. 컬럼을 추가할 때 이 함수를 확인해야 한다.
- **노쇼 신고 화면이 없다** — 대시보드에 `pending_no_shows` 는 세지만 처리할
  화면이 없다. 자동 판정(인정·무응답)만 있고 다툼이 생기면 손댈 수 없다.
